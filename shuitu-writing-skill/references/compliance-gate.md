# 第一层：合规闸门（Compliance Gate）

> **这是写作动作之前的第一道也是不可绕过的一道关。**
> 任何章节在生成正文之前，必须先执行本闸门；`blocked=true` 时**禁止继续写作**。
> 全部规则以声明式形式写在本文件与 `rules.json` 中。**有 Python 时跑 `scripts/check_gate.py`；没有 Python 时，按本文件的流程手工执行，结论必须一致——规则不允许只存在于代码里。**

---

## 一、输入 / 输出

**输入**

| 参数 | 必填 | 说明 |
|---|---|---|
| `chapter` | 是 | 模板章节号，如 `1.1.1`、`2.3`、`5.1`。若传入容器节点（如 `1.1`），自动展开为其内容节点（`1.1.1`、`1.1.2`） |
| `province` | 否 | 项目所在省（自治区、直辖市）。**不填则地方级 Zone A 依据不激活** |
| `city` | 否 | 项目所在地市/县，用于激活市级依据 |

**输出（固定 JSON）**

```json
{
  "chapter": "2.3",
  "expanded_nodes": ["2.3"],
  "hard_constraints": [
    {
      "source": "GB 50433-2018",
      "source_file": "md库\\01-政策法规\\03-技术标准\\GB 50433-2018_生产建设项目水土保持技术标准.md",
      "clause": "2.3",
      "requirement": "2.3 工程占地 根据本标准第4.2.1条第4款的规定编制，并符合本标准第4.2.4条的有关规定。水土保持方案对工程占地有调整的应说明。",
      "origin": "inherited",
      "scope": "national",
      "status": "现行有效",
      "match_score": 4
    }
  ],
  "warnings": [],
  "provisional": true,
  "blocked": false,
  "block_reason": null,
  "constraint_scope": { "node_specific": 2, "inherited": 9, "clause_count": 7 }
}
```

字段说明：

- `hard_constraints[].requirement` — **必须是所引文件正文的逐字片段**，截断时末尾标 `…（截断）`。禁止改写、概括、跨条款拼接。
- `hard_constraints[].clause` — 原文条款号（法条为「第X条」，标准为章节号）。取不到编号时填 `（段落）`。
- `hard_constraints[].origin` — `node_specific`（该依据的 `chapter_relevance` 直接含本节点）或 `inherited`（含 `全域` 或祖先节点）。**两者分开统计，阈值只对前者生效。**
- `warnings` — 非阻断性提示（依据过期、范围未激活、状态待核验等）。
- `provisional` — 本轮依据中有 `待确认` 字段时为 `true`。允许继续写作，但**送审前必须强制阻断**要求人工确认。
- `blocked` / `block_reason` — 见 §三。

## 二、执行流程（六步，顺序不可调换）

### 第 1 步：展开章节
传入容器节点时展开为其内容子节点（容器节点自身不承接要求）。内容节点清单见 `template-tree.json` 的 `node_kind == "content"`。

### 第 2 步：取用适用依据
从 `zone-a-index.json` 逐条判断 `applies`：

1. **章节匹配**：`chapter_relevance` 含 `全域` → 适用（inherited）；含本节点号 → 适用（node_specific）；含本节点任一祖先号 → 适用（inherited）；否则不适用。
2. **范围激活**：
   - `scope: national` → 恒常激活
   - `scope: provincial` → 仅当声明省份且与文件匹配（河南省文件对应含"河南"的省份值）
   - `scope: local` → 仅当声明了对应地市
   - `scope: 不适用` → 参考层，永不参与
   未激活时写入 `warnings`，**理由必须具体**（"未声明项目所在省份，地方级依据「X」未激活"）。

### 第 3 步：按 status 分流
以 `status` 前缀判定：

| 归类 | status 前缀 | 处理 |
|---|---|---|
| 现行 | `现行有效`、`试行有效` | 进入第 4 步 |
| 过期 | `已废止`、`已失效`、`已被代替`、`试行期满`、`未生效` | 写入 `warnings`（`status_stale`），附 `superseded_by` 指引，**不进入 hard_constraints** |
| 排除 | `待核验`、`编制阶段` | 写入 `warnings`（`status_excluded`），**只能作资料线索，不得作为合规依据** |
| 未知 | 其他 | 写入 `warnings`（`status_unknown`），要求人工确认 |

### 第 4 步：抽取条款（逐字）
在该文件正文中定位与本章节对应的条款：

- **法条**：按「第X条」切分
- **标准**：按行首编号（`4.2.1 …`）切分
- **其余**：按段落切分，条款号记 `（段落）`

**匹配打分（决定取舍）**

| 分 | 条件 |
|---|---|
| 4 | 条款号**等于**本节点号（或带附录前缀如 `B.1.1.1`）**且**正文含本节点核心概念或关键词 |
| 3 | 正文含本节点核心概念（节点标题去括注后的文本） |
| 2 | 正文含本节点关键词之一（见 `rules.json` 的 `node_keywords`） |
| 1 及以下 | 丢弃 |

> **为什么条款号相符还不够**：不同文件的同名号含义完全不同。GB 50433-2018 的 `5.1` 是「防治区划分」，而模板的 `5.1` 是「渣土来源及流向」。只看号会张冠李戴，所以**号相符必须同时内容相符**才给 4 分。

**剔除以下内容**（它们不是规范要求）：
- 表格标记（`<table>`、`colspan`）
- 目录行（连续 `...`）
- **条文说明/解释性文字**（含"本条为强制性条文"、"【条文说明】"、"本条中的"）——文件在读取时已在「条文说明」标题处截断
- 网页抓取残留（"您现在的位置"、"中国政务"、"返回顶部"等）
- 编制依据罗列（前 220 字内出现 3 个以上 `《`）

**精度优先**：同一文件内若已取到 4 分条款，则丢弃该文件的 2 分条款。

### 第 5 步：判定 blocked
`blocked=true` **仅当**：本节点没有任何现行 Zone A 依据可覆盖（`node_specific + inherited == 0`）。

此时：
- 若库中存在相关但状态过期的依据 → `block_reason` 必须点名该依据、其状态与 `superseded_by`
- 否则 → `block_reason` 说明需补充规范来源

**不构成 blocked 的情形**（只写 `warnings`）：
- 某条依据过期，但仍有其他现行依据覆盖同一约束
- 依据关键字段为 `待确认`（→ `provisional=true`）
- 地方级依据未激活
- 有现行依据但未定位到直接对应条款（→ `no_clause_hit`，**需人工确认后再写作，不得默认为"无要求"**）

### 第 6 步：交付下游
通过闸门后，`hard_constraints` 交给第二层模板编排器，与 `template-tree.json` 的本节点 `required_content_points` 合并生成写作指令。

## 三、四条铁律（自检项）

1. **Zone B 永不参与合规判断。** 本闸门只读 `zone-a-index.json`。任何 `zone=B` 的文件都不得出现在 `hard_constraints` 或 `blocked` 判定中。Zone B 只在闸门通过后由第二层作为**写作表达参考**引入，且必须带限定语。
2. **Zone C 永不参与合规判断，也不得作为"曾经通过"的背书。** 本闸门**只读 `zone-a-index.json`**，因此 Zone C 在结构上不可能进入 `hard_constraints` 或 `blocked` 判定（这是设计保证，不是靠自律）。
   - 已批准方案只在**当时的标准体系**下被接受——标准会变，模板也会变（老八章 → 新十章）。
   - **禁止**任何形如"该做法已通过部批，故合规"的推理。
   - 当 Zone A 对某一问题没有明确规定时，必须输出：
     > 「**Zone A 未明确规定，以下为参考写法，需人工判断**」
     而**不得**以某范例的做法填补空白。
3. **`blocked=true` 时不得继续写作。** 下游必须停止，不得"先写着再补依据"，且**不得检索 Zone B / Zone C**。
4. **不得编造条款。** `requirement` 必须能在 `source_file` 中逐字检索到。定位不到就输出 `no_clause_hit` 警告，而不是拼一句像样的话。

## 五、已知限制（必须如实告知）

1. **`provisional` 普遍为 true。** 因为 Zone A 中 55 处 `doc_number`、9 处 `effective_date` 等仍为 `待确认`。这是数据现状，不是闸门缺陷；补齐后自动消除。
2. **条款定位基于关键词与条款号，不是语义检索。** 对内容高度专门化的节点（模板自有节点、矿山生态修复类），能定位到的 Zone A 条款本就稀少——**这是知识库的真实覆盖面，不是脚本漏检**。
3. **模板类文件的条款会出现在 `hard_constraints` 中**，与 `template-tree.json` 的节点要求有重叠。模板是骨架（由第二层直接施加），此处重复出现属冗余但无害；下游可据 `source_file` 是否属模板类自行去重。
4. 摘要版《编制模板》文件已列入 `rules.json` 的 `deprioritized_sources`：**仅在权威来源（附件1/2/3）未提供足够条款时才作为兜底**，避免其已知缺失被继承进方案。
