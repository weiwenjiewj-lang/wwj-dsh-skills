## 二、资料调用机制（**禁止全文检索** —— 强制）

> **本节是硬规则。** 知识库已含 60+ MB 级别的单文件，直读或全文检索是最大的 token 黑洞。

### 三层取用顺序（**只能按此顺序**）

| 顺序 | 手段 | 命令 | 说明 |
|---|---|---|---|
| ① | **分章取用**（首选） | `python kb_lookup.py --chapter 9.1.2` | 按模板节点列出该节全部 Zone A/B/C 文件**路径 + 元数据**，不返回正文 |
| ② | **专项索引** | `--ask` / `--ask-a` / `--ask-c` / `--ask-style` / `--map` / `--chapters` | 物种、参数、工法、规范、范式 |
| ③ | **全库精确检索** | `python kb_read.py --find <词>` | 走倒排索引，**全库 371 文件 / 81.7 万行零盲区**，毫秒级，只返回位置 |
| ④ | **按位置取原文** | `python kb_read.py --read "<文件>" --line N`<br>`python kb_read.py --section "<文件>" --heading "<标题>"` | **把位置变成正文**——取多少由 `--context` 控制，永不整文件倾倒 |

> **③④ 是 2026-09 新增能力**。此前流程止步于"定位 + 人工开编辑器"：
> `kb_lookup.py --find` 只给「文件名+行号+≤80 字片段」，AI 拿不到正文，
> 必须人工介入——这是"查得到"与"用得上"之间的断点。现由 `kb_read.py` 补上。

### 倒排索引（`kb_read.py` 专用）

全库倒排索引，**371 个文件 / 81.7 万行 / 566 MB 全部覆盖，零盲区**
（`python build_search_index.py --verify` 可随时复核）。

| 项 | 值 |
|---|---|
| 索引文件 | `references/search_index.kbx`（惰性二进制 v5，**41.5 MB**） |
| 加载耗时 | **1.9 秒**（惰性：只建「词→偏移」表，词条正文查到才解析） |
| 单次查询 | **<1 毫秒** |
| 分词 | 中文 2~3 字 n-gram + ASCII 词（标准号带空格整串识别） |

> ### ⚠ 检索口径与已知边界（2026-09 修复，**用前必读**）
>
> 索引是**近似索引**，不是全量全文库。它速度快、精度高，但**不保证 100% 召回**：
>
> | 场景 | 索引行为 | 要全量时用什么 |
> |---|---|---|
> | 2~3 字中文词、标准号、英文词 | **100% 覆盖**（已实测 120 中文词 + 50 ASCII 词逐一对齐真值） | 索引即可 |
> | 高频词（如「水土」「保持」「标准」） | 每词上限 400 处，超出部分不进索引 → 出现**文件覆盖下降** | `kb_lookup.py --find` |
> | ≥4 字长查询（如「水土保持」） | 走 2-gram 交集，**精度 100% 无假阳性**，召回约 80% | `kb_lookup.py --find` |
>
> `kb_read.py --find` 在检测到上述近似情况时会**主动打印提示**，不会让你误以为
> 看到的是全量结果。**要零遗漏一律用 `kb_lookup.py --find`**
> （流式扫描全库，100% 覆盖，只回位置）。
>
> **三条已修复的检索误判**（均由本轮对抗性测试发现）：
>
> 1. **截断吃掉文件覆盖**：旧实现 `postings[:400]` 是"取文档序前 400 处"，
>    热门词的前 400 处集中在最前几个文件里，于是「保持」只剩 **10/348 个文件（2.9%）**、
>    「防治」只剩 **4/305（1.3%）**。改为**按文件聚合 + 轮转分配行预算**后全部回到 100%。
> 2. **子串回退假阳性**：查询一个全库**不存在**的短语时，只要其某个 3 字片段存在，
>    就返回该片段的结果——实测 `不存在词xyz`（真值 0 处）返回了 **136 个文件**。
>    现在回退结果**一律逐行回原文核对**，核对不过就如实报「未命中」。
> 3. **交集塌缩**：2-gram 交集在窗口缺失时静默跳过，且返回时截断窗口列表，
>    导致「水土保持」只报 8 处（真值 2594 处）。现在缺失窗口会显式告警，窗口不再截断。

> **v5 格式（2026-09）**：索引从 98.2 MB → **41.5 MB（−58%）**，查询结果完全等价。
> 三代格式的演进：
> · **v3 → v4（98.2 → 65.5 MB）**：消除「词串在 header 与 body 各存一遍」的冗余；
>   词表改前缀压缩（21.2 MB → 9.4 MB）。
> · **v4 → v5（65.5 → 40.9 MB）**：对词表、偏移表与 body **整体做 zlib 无损压缩**
>   （词表 12.57 → 5.52 MB、偏移 3.13 → 1.80 MB、body 49.7 → 33.1 MB）。
>   zlib 是**标准库自带**，不引入任何新依赖；body 是**惰性解压**的，
>   `--find` 这类只回位置的命令根本不解析 postings，因此不付解压代价。
>   （其后修复「截断吃掉文件覆盖」时，轮转分配让每词多留一些行，体积回到 **41.5 MB**。）
>
> **顺带修掉的性能债**：词表解码原为逐条调用 varint 函数（239 万 × 2 = 478 万次调用），
> 占整个加载耗时的 **51%**（1.37s / 2.67s）。利用「绝大多数 varint 是单字节」这一事实
> 内联快路径后，加载 **2.67s → 1.9s**。修复后 **v5 反而比 v4 更快**（1.9s vs 2.2s）。
> 正确性用 410 个 varint 边界值（0/127/128/16383/16384/10⁹ 级）逐值比对验证。
>
> **校验**：238.9 万词条**逐条解析，异常 0 条**；读写两侧（`pack_index.py` / `kb_read.py`）
> 同时支持 v3/v4/v5，老索引无需重建即可继续查询；`build_search_index.py --build`
> 按 **v5 → v4 → v3** 依次尝试，任何情况下都留下一个可用索引。

**为什么是 2~3 字而非 2~4 字**：实测 4 字 n-gram 单层产出 332 万词条（占索引 58%）
却只带来边际召回。更长的查询（如「表土剥离厚度」）由 `--find` 的
**2-gram 交集**处理——取各 2 字窗口命中文件的交集，既定位精确又不膨胀索引。

**图片不再是盲区**：原 `--find` 跳过 base64 图片行以提速（452MB→99MB），
代价是图片位置不可检索。现索引把图片**折叠成锚点**（只记行号与字节数），
`python kb_read.py --images "<文件>"` 可查全库 **8525 张图**的位置。

> **图片降采样（2026-09）**：库内内嵌图片原有 340.6 MB（占全库 51%），
> 由 `scripts/shrink_images.py` 做**自适应重编码**——按图片边缘能量自动定质量下限
> （文字/图纸类保住 72，照片类可降到 52），并只在「重编码后更小」时才替换。
> 实测 Zone B 436.3 → 384.1 MB、Zone C 109.9 → 98.7 MB，共省 60.5 MB，
> 抽检 30 张全部可正常解码，密集等高线图纸在 39% 体积下仍清晰可读。
> `--check` 只预演不写盘，`--apply` 才执行；**Zone A 不做任何压缩**（红线条款须逐字保真）。

### 明令禁止

- ✗ **不得**用 `grep` / ripgrep 扫 `md库` 全库
  （改用 `kb_read.py --find`——同样全库覆盖，但它有索引、毫秒级，且只返回位置不吐正文）
- ✗ **不得**对 `md库` 做递归 `read`
- ✗ **不得**把 `asset-map.json`（600+ KB）整个读进上下文——它是**给脚本用的**，
  AI 只能通过 `--chapter` 间接取用
- ✗ **不得**用 `--context` 一次取超过 200 行（工具本身有硬上限，防烧预算）
- ✗ 优化、再开发本技能时，同样**不得**为"了解库内容"而全文检索；应读 `references/*.json` 索引

### 支撑资产

| 文件 | 作用 | 谁读 |
|---|---|---|
| `references/asset-map.json` | 节点级 / 章级资源地图（路径+元数据，无正文） | **仅脚本**，经 `--chapter` / `--chapters` 间接使用 |
| `scripts/build_asset_map.py` | 从三个 zone 索引重建 asset-map | 数据变更后运行 |
| `references/zone-a-index.json` / `zone-b-index.json` / `zone-c-index.json` | 分层条目索引（含 `chapter_relevance`） | 脚本 |
| `references/zone_c_style_samples.json` | 写法范式样本（334 条，已脱敏，含段落功能/句式骨架/论证链） | 脚本 → `zss` 注入 |

## 三、知识库位置与时效性

**知识库随技能包一同交付**，默认位置为**技能包内的相对目录**：

```
<技能包>/
├── SKILL.md
├── references/          ← 索引快照与规范文件
├── scripts/
└── vault/               ← 知识库（库根）
    ├── md库/            ← 371 个 md，三层分区
    │   ├── Zone A - 规范层/     (75)
    │   ├── Zone B - 参考层/     (204)
    │   └── Zone C - 应用范例/   (91)
    └── .obsidian/       ← Obsidian 库配置
```

**路径解析集中在 `scripts/vault_paths.py`**（唯一入口）：

| 优先级 | 来源 | 说明 |
|:--|:---|:---|
| 1 | 环境变量 `DSH_WS_VAULT` | 显式指定，换库位置/临时挂载用 |
| 2 | `<技能包>/vault/` | **默认**，技能自包含 |
| 3 | `<技能包>/` | 兼容"md库 直接放在技能根"的布局 |

**三种场景的实测行为**（`python scripts/vault_paths.py` 可自检）：

| 场景 | 行为 |
|:---|:---|
| 未设环境变量 | 用 `<技能包>/vault/`，读 371 个 md |
| `DSH_WS_VAULT` 指向有效外部库 | **以它为准**（可换库位置） |
| `DSH_WS_VAULT` 指向无效路径 | **明确告警并停止**，`kb_lookup --map` 输出 `⚠ 知识库不可达` |

> ⚠ **指向无效路径时不会自动回退**到技能包内库——
> 那会让使用者以为"换库成功了"，实际读的却是旧库，是比报错更危险的失败。

> **为什么知识库放在 `vault/` 子目录而不是技能根**：
> 索引构建会从库根**递归扫描** md，若库根就是技能根，
> 会把 `SKILL.md`、`README.md`、`references/*.md` 一并当成知识库条目
> （实测多出 15 个假条目并触发快照漂移告警）。
> `vault/` 子目录把技能自身的文档与知识库天然隔离。

> **为什么改用相对路径**：原先是硬编码的 `E:\obisidian\...` 绝对路径，
> 7 个脚本各写一份。技能包搬到别的机器、或知识库换位置，这些路径必然失效——
> 而且**漏改的那处不会报错**，只会静默地把知识库当"不可达"，输出过期警告或空依据。
> 现在集中在一处解析，规则只定义一次。

**Obsidian 使用**：把 Obsidian 的 vault 切到 `<技能包>/vault/` 即可（`.obsidian` 配置已随库迁入）。

> 库不可达时（目录缺失/未就绪），脚本**不阻断**写作，但会在输出中强制携带
> 「知识库不可达……仅能使用索引快照」警告（`stale=true`）。

- **运行时优先实时读库**；`references/*.json` 是随技能携带的**索引快照**，仅作离线兜底。
- 快照年龄超过 **30 天**，或知识库文件清单（路径+大小+修改时间）与快照记录不一致时：
  **必须自动重建快照并重新校验 Zone A 索引，然后才允许写作**；
  未重建前所有输出必须带「知识库索引可能过期，合规结论未经验证」的显式警告。
  **绝不静默使用旧索引。**
- **自动执行**：`check_gate.py` / `write_chapter.py` / `check_draft.py` 每次运行都会比对
  `vault_manifest.json`（阈值与判定条件见 `rules.json snapshot_gate`）；
  过期**不阻断**写作（时效性 ≠ 依据缺失），但输出强制携带警告与重建指引
  `python "$SK\scripts\rebuild_index.py" --rebuild`。
  `rebuild_index.py --check` 可单独做漂移检测。
- 时效性监控清单 `source_watchlist.json` 记录每个 Zone A 文件的
  `current_status`、`last_checked`、`next_check_date`、`official_lookup_url`；
  发现被替代/废止时生成变更包
  （`change_type` / `old_doc` / `new_doc` / `effective_date` / `affected_chapters` / `action_required`），
  并据此更新 Zone A 索引与缺口报告。

## 四、Token 节约机制（实测数字）

知识库 371 个 md / **633 MB**。三层机制已内置：

### ① 增量缓存 —— 不要重复全量读库

四个 `build_*.py` **默认走缓存**：知识库未变更时**直接跳过重建**（0.1s 级）。

```bash
python "$SK\scripts\build_species_index.py" --build    # 未变则 0.1s 跳过
```

| 脚本 | 首建 | 重建 |
|:---|---:|---:|
| build_species_index | 20.2s | **0.13s** |
| build_measure_methods | 20.5s | **0.11s** |
| extract_style_samples | 7.6s | **0.10s** |
| build_design_params | 1.8s | **0.12s** |

> 缓存键是 `(路径, mtime, 大小)`，**文件一改即失效**，不会用到旧内容。
> 需强制重建加 `--force`；缓存可随时 `python "$SK\scripts\kb_cache.py" --clear`。

### ② 指令包默认精简

`write_chapter.py` **默认输出精简包**（V2：键名速记 + 超长截断 + 去元数据壳 + 去重复）：

| 章节 | 完整包 | 精简包 | 省 |
|:---|---:|---:|---:|
| 1.1 | 51.7 KB | 31.8 KB | 38.5% |
| 2.4 | 20.9 KB | 12.2 KB | 41.5% |
| 7.7 | 69.5 KB | 48.6 KB | 30.1% |
| 9.1.2 | 39.8 KB | 29.0 KB | 27.1% |
| **合计（11 节）** | **306.6 KB** | **210.3 KB** | **31.4%** |

> 等价性由 `python "$SK\_meta\verify_equiv.py"` 断言（11 节逐项计数必须全等）。
> 调试指令包本身时才加 `--full`；给人看才加 `--pretty`。
> 包内为**短键名**，对照见 `references/key-alias.md`（一次读入，全书复用）。

### ③ **绝不直读、也不全文检索知识库**（最重要）

体积分布（`kb_lookup.py --stats` 实测）：

| | 大小 | 约 token |
|:---|---:|---:|
| 最大文件（生产建设项目水土保持设计指南） | 64 MB | **1900 万** |
| 第二（北京市土壤流失方程） | 26 MB | 780 万 |
| **中位数文件** | 400 KB 级 | **11 万+** |

**一次直读就可能烧掉整个对话预算。** 因此**两条都禁止**：直读原文、grep 全库。

| 要找什么 | 正确入口 | 禁止做法 |
|:---|:---|:---|
| 某节有哪些依据 | `--chapter <节点>` | grep Zone A 全部 md |
| 规范条款 | `zone-a-index.json`（`--ask-a`） | grep Zone A 全部 md |
| 写法范式 | `zone_c_style_samples.json`（`--ask-style`） | grep Zone C 正文 |
| 物种知识 | `species_index.json`（`--ask <物种>`） | grep 专著找树草种 |
| 设计参数 | `design_params.json`（`--ask <参数>`） | 翻标准原文找表格 |
| 措施工法 | `measure_methods.json`（`--ask <措施>`） | 翻标准原文找条文 |
| 项目事实 | `台账.json` | 回读原始资料 |

> `--find` **仅作索引查不到时的最后兜底**，且它**只返回文件名+行号+≤80 字片段**
> （默认 5 条上限），**永不打印正文**——实测单次仅 681 字符 ≈ 194 token。
> 但它仍然要扫全库文本（耗时），**能不用就不用**。
>
> **需要正文时**：先用 `--chapter` 定位到具体文件，再**只读那一份**。
> 超大文件（如两部指南 60 MB / 26 MB）**不要整读**，用 `read` 的 `offset`/`limit` 分段取。

**四个索引的重建命令**（知识库更新后需重跑）：

```bash
python "$SK\scripts\build_species_index.py" --build      # 资产 D
python "$SK\scripts\build_design_params.py" --build      # 资产 E
python "$SK\scripts\build_measure_methods.py" --build    # 资产 F
python "$SK\scripts\extract_style_samples.py" --build    # 资产 C
```

## 五、新增资料入库流程（**PDF/docx 走云服务转换**）

本技能**不在本地跑 PDF 转换**（本地跑需下载数 GB 模型且吃内存）。
转换走**云服务插件**，转完会得到 `xxx.md` + 一个图片文件夹，**必须按下列步骤入库**：

```powershell
# 1) 用云服务把 PDF 转成 md（得到 xxx.md + images/ 之类的图片目录）

# 2) 关键一步：把图片收进包内 .assets/，md 内改相对路径引用
python "$SK\scripts\inline_images.py" --dir <云服务输出目录>
#    → 把 ![](images/xxx.jpg) 移入 vault\.assets\<tag>\ 并改写为相对路径
#    → 也可只处理单个文件：python inline_images.py 某文件.md
#    → 入库前自检：python inline_images.py --check 某文件.md

# 3) 补 frontmatter（zone / doc_type / compliance_relevance / style_role 等）

# 4) 放入对应目录 → 重建索引
python "$SK\scripts\rebuild_index.py" --rebuild
```

> **为什么必须收进包内 `.assets/`**：知识库规约是「图片存包内 `.assets/`，md 用相对路径引用，
> **禁止外链**」。若直接放 `![](images/xxx.jpg)` 这类外链，**脱离原目录即失效**。
> `.assets/` 目录随包分发，用 `../` 相对路径回溯，**任何深度都能解析**
> （已实测 8477 处引用 **0 失败**）。

> **历史包袱说明**：`inline_images.py` 原实现是「转 base64 内嵌 + 删除图片目录」。
> 2026-09 修订为「移入包内 `.assets/` + 相对路径」——
> 原因是实测 base64 的 **4/3 膨胀**让 md 膨胀到 503 MB（占全包 91%），
> 而剥离后 md 仅 **113.4 MB**（降 77.8%），且**检索通道同步瘦身**。
> 脚本名与 `--check` 退出码语义保持不变，避免破坏既有调用。
