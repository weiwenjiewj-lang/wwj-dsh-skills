# 水土保持方案编制（通用）

按水利部 **办水保函〔2026〕232号**《生产建设项目水土保持方案编制模板》的章节结构逐节点产出方案内容。
**技能本身不含任何具体项目信息**；项目信息由使用者以「项目数据包」在运行时提供。

> **本文件只留"每次执行都必须知道"的内容。** 知识库分区、资料调用细节、时效性监控、
> 入库流程、文件树、实测数字等，已外移至 `references/kb-and-tokens.md`（需要时再读）。
> 这样每次加载技能的常驻开销从 ~11,400 token 降到约 1/3。

**按需加载的资源**（不要在开始时全读）：

| 何时读 | 读什么 |
|:---|:---|
| 要查知识库/资料调用/入库 | `references/kb-and-tokens.md` |
| **要全库检索或取原文** | 直接用 `scripts/kb_read.py`（`--find` / `--read` / `--section` / `--outline` / `--images`） |

## 一、六条铁律（任何情况下不得违反）

1. **知识分三层，低层不得覆盖高层。**
   - **Zone A（规范层）**：法律、行政法规、部门规章、规范性文件、国家标准、行业标准——绝对红线。
   - **Zone B（参考层）**：专家专著、学者论文、学位论文、技术手册、团体标准、非规范性规划/报告——**仅用于写作表达、论证逻辑与案例参考**。
   - **Zone C（应用范例层）**：水利部或省级已批准/通过审查的典型方案——**仅用于写作风格、章节展开方式、表达逻辑、表格设计**。
   - 冲突时**以 Zone A 为准**；Zone B / Zone C 的冲突内容**一律丢弃**（是丢弃，不是标注保留）。
   - 详见 `references/metadata-spec.md`、`references/zone-b-usage.md`、`references/zone-c-usage.md`。

2. **模板是唯一骨架。** 章节号与标题逐字取自 `references/template-tree.json`，**不得自行增删改章节**。
   **Zone C 不得作为"章节完整性"判据**——老八章范例缺第4章（表土）、第5章（弃渣场）是**范例的结构缺陷**，不是可以略过的依据。

3. **不得编造。** 所有法规、标准、条款必须来自 `references/zone-a-index.json` 指向的知识库文件；
   `hard_constraints[].requirement` 必须是原文逐字片段。数据缺失时留占位符，不猜数。

4. **Zone C 不得作为任何合规结论的依据。** 不得写入 `hard_constraints`，不得参与 `blocked` 判定，
   不得引入其具体项目数据（名称/地点/数字/单位名），**不得因其"曾经通过"而推定其做法在当前标准下仍然合规**。
   **Zone A 未明确规定时**，必须输出「**Zone A 未明确规定，以下为参考写法，需人工判断**」，不得直接采用 Zone C 的做法。

5. **零项目残留。** 正在编制的项目信息**一律不得写回本技能目录，也不得写回 Obsidian 知识库**。
   项目数据只允许存在于当前会话或该项目自己的工作区。

6. **绝不直读知识库原文。** 知识库 371 个 md / **566 MB**，中位数文件 400 KB ≈ **11.6 万 token**，
   最大文件 60+ MB ≈ **1800 万 token**——**一次直读就能烧掉整个对话预算**。
   取知识一律走索引通道，**禁止整文件 read，禁止 grep 全库**：

   | 要什么 | 用什么 |
   |---|---|
   | 哪些资产可用 | `kb_lookup.py --map` / `--chapter 9.1.2` |
   | 某物种/参数/工法/规范的结论 | `kb_lookup.py --ask` / `--ask-a` / `--ask-c` / `--ask-style` |
   | **全库找某词在哪** | `kb_read.py --find <词>`（倒排索引，毫秒级；**要零遗漏见下方说明**） |
   | **取某处的正文** | `kb_read.py --read "<文件>" --line N --context 30` |
   | **取某一节正文** | `kb_read.py --section "<文件>" --heading "<标题>"` |
   | 某文件有哪些标题 | `kb_read.py --outline "<文件>"` |

   > **`--find` 的召回口径（务必知道）**：倒排索引对 2~3 字中文词、标准号、英文词的
   > 覆盖是 **100%**；但**高频词**（每词 400 处上限）和 **≥4 字长查询**（2-gram 交集）
   > 属于**近似结果**——精度 100%（无假阳性），召回约 80%。
   > 工具在这种情况下会**主动打印提示**，不会让你误以为看到的是全量。
   > **要零遗漏一律用 `kb_lookup.py --find <词>`**（流式扫描全库，100% 覆盖）。
   > 详见 `references/kb-and-tokens.md` 的「检索口径与已知边界」。

   **取文必须限量**：`--context` 默认 25 行、硬上限 200 行；输出前工具会报本次 token 估算。
   细节见 `references/kb-and-tokens.md`。

## 二、写作流程（十二步，顺序不可调换）

「十二步」不是十二个动作，而是**四个阶段**：**备料 → 立骨架 → 写正文 → 校核收口**。
每步都有对应脚本，脚本只执行 `references/rules.json` 里的规则，不自带阈值。

> **检查点约定**：标 🛑 **STOP** 的是**强制停止点**——必须停下等人工确认，不得自行续跑。
> 标 🔴 **CHECKPOINT** 的是**自检点**——跑脚本核对，通过方可进入下一步。
> 检查点不是可选项，是流程的一部分；跳过即视为流程未执行。

```
【阶段一 备料】
第1步  喂料：把可研/初设/地勘/主体设计等原始资料交给 ingest.py，产出项目数据包 json
       （字段抽取 + 单位归一 + 冲突标注；抽不到的留空并列入补数清单，不猜）
第2步  核数：核对数据包里的「待人工确认（冲突）」项，逐项定值
第3步  立账：把已定事实写入事实台账 ledger.py（跨章同一事实只有一个值，谁先写谁定，
       后来者与台账冲突则拒绝写入并提示）
【阶段二 立骨架】
第4步  过闸门：check_gate.py ← 不可跳过、不可后置（blocked=true → 停止，不得写作）
       🛑 STOP：闸门结果必须先人工确认，blocked=true 时不得进入第5步
第5步  搭骨架：outline.py 产出全书 95 节点骨架（标题逐字来自模板，含每节字数预算、
       必覆盖内容点、必备表骨架、计算项位置）
       🔴 CHECKPOINT：核对节点数=95、标题逐字来自模板、无模板外章节号
【阶段三 写正文】——每个节点重复第6～9步
第6步  取指令包：write_chapter.py 一次拿到该节点的模板内容点、Zone B 范式、Zone C 表达层、
       篇幅预算、台账事实、计算项与闸门结果（blocked 时不返回 Zone B / Zone C）
第7步  算数：calc.py 出该章计算书（公式 → 代入 → 中间量 → 结果 → 依据），
       缺项目输入一律输出【待填：…】并标「缺数据不可计算」，绝不用默认值兜底
       🔴 CHECKPOINT：计算书须含中间量；缺输入项已显式标注，未用默认值兜底
第8步  写正文：按模板内容点逐条落笔；数据缺失写【待填：字段名】；条款逐字引用
第9步  单节回检：check_draft.py 查覆盖/占位符/数字/标题/文风/篇幅/台账（写完一节就查，
       不要等全书）
       🔴 CHECKPOINT：C1–C7 全过或偏离项已逐条处置，方可进入下一节
【阶段四 校核收口】
第10步 全书终检：check_plan.py 查 95 节点覆盖、表1 特性表 55 栏、附件附图清单、跨章口
       径一致性、全书篇幅折算、占位符清零
       🔴 CHECKPOINT：占位符必须清零，或已全部转入「补数清单」
第11步 台账复核：ledger.py --check 用定稿正文反查台账，冲突逐条处理
第12步 交付：占位符清零或转「补数清单」；已知问题写进方案说明，不带病送审
       按「§九 交付标准」产出 Word 文件并自动打开
       🛑 STOP：交付前必须人工确认——占位符已清零、provisional 项已核实、已知问题已写明
```

**四个阶段的分工（为什么不能省）**

| 阶段 | 脚本 | 不做的后果 |
|---|---|---|
| 备料 | `ingest.py` / `ledger.py` | 同一事实在 2、6、7、9 章各写一个值，评审一眼看出矛盾 |
| 立骨架 | `outline.py` / `budget.py` | 前松后紧：前 3 章写掉一半篇幅，后 7 章只能一笔带过 |
| 写正文 | `write_chapter.py` / `calc.py` | 指标算错但前后一致，机械校核查不出来 |
| 校核 | `check_draft.py` / `check_plan.py` | 漏节点、表1 缺栏、占位符留在定稿里 |

**为什么闸门必须在参考素材之前**：若先取参考素材，写作者会先形成"写法与结论"，再去找规范背书，
极易把 Zone B 的方法论、或 Zone C 的"曾经通过的做法"包装成规范要求。先取红线、再取表达，红线才不会被表达习惯带偏。

**Zone C 的特殊限制**（详见 `references/zone-c-usage.md`）：
- **禁止按章节号挂载**——已批准方案几乎都是老八章结构（GB 50433-2018 附录B），与 2026 版 10 章**同号不同义**
  （老 `1.5`＝防治目标，新 `1.5`＝水土流失预测结果）。检索**只能走 `topic_tags` 主题挂载**；
  `chapter_mapping != verified` 的范例不得挂载。
- **默认关闭、按需开启**：只在 Zone A 专属依据为 0 的缺口节点注入，每次最多 2 条、每条 ≤150 字结构摘要。
- **第二个合法用途**：作为**知识库缺口探针**——范例出现 Zone A 完全未覆盖的审查关注点时，记入缺口报告（仍不得用于合规判定）。
- **唯一第三个用途**：Zone C 的**篇幅占比实测值**用于全书字数分配（`rules.json length_budget.chapter_shares`）——
  只借"哪一章通常写多少"这一分布特征，不借其内容与结论。

**执行方式（有 Python）**

```powershell
# $SK = 本技能包所在目录（本机路径如下，直接可用）：
# $SK = "<DSH_HOME>\skills\shuitu-writing-skill"
# 全部命令在**项目工作区目录**下运行，产物（数据包/台账/稿/报告）落在工作区。
# 脚本拒绝把任何产物写进技能包或知识库（铁律5 零项目残留），路径非法即停并说明原因。
# 退出码：0 通过 · 1 有需处理项 · 2 输入/用法错误（含章节号不在模板里；无可信结果） · 3 闸门 blocked 禁止写作。
# 机读输出：多数脚本有 --json-only（analyze_gaps 用 --json），stdout 为纯 UTF-8 无 BOM。

# 阶段一：喂料 → 核数 → 立账
python "$SK\scripts\ingest.py" --source 可研报告.docx --source 地勘.md --out 数据包.json
python "$SK\scripts\ledger.py" --file 台账.json --set "防治责任范围面积=86.5" --unit hm² --chapter 1.6.1
python "$SK\scripts\ledger.py" --file 台账.json --set "防治标准执行等级=一级标准" --chapter 1.6.1

# 阶段二：闸门 → 骨架
python "$SK\scripts\check_gate.py" --chapter 2.3 --province 河南省          # 报告表加 --report-form
python "$SK\scripts\outline.py" --province 河南省 --out 方案骨架.md          # 全书 95 节点
python "$SK\scripts\outline.py" --chapter 2 --province 河南省 --out 第2章骨架.md

# 阶段三：指令包 → 计算书 → 单节回检
python "$SK\scripts\write_chapter.py" --chapter 1.1 --province 河南省 --out 指令包.json
python "$SK\scripts\calc.py" --chapter 7.3.2 --data 数据包.json --out 计算书_7.3.2.md
python "$SK\scripts\check_draft.py" --draft 稿件.md --chapter 1.6.2 --province 河南省 --ledger 台账.json

# 阶段四：全书终检 → 台账复核
python "$SK\scripts\check_plan.py" --draft 全书.md --province 河南省 --ledger 台账.json --out 终检报告.md
python "$SK\scripts\ledger.py" --file 台账.json --draft 全书.md --check

# 自检：计算项与数据包字段是否对应（改过 rules 的 calc_engine 后必跑）
python "$SK\scripts\calc.py" --audit
```

> **数据包支持三种形态**：`ingest.py` 产出的规范形态、**手写扁平形态**（`{"挖方":"15.2"}`）、列表形态。
> 手写小数据包试算时直接用扁平格式即可，引擎会提示已读入多少字段。

**执行方式（无 Python）**：按 `references/compliance-gate.md` 的六步手工执行闸门，
按本文件第三～五节手工组装写作指令。规则全部明文写在 `references/rules.json` 与
`references/compliance-gate.md` 中，**不允许出现只写在代码里的规则**，两种执行方式结论必须一致。

**脚本失败时的三段式处置**（脚本报错不得静默绕过，按退出码分流）：

| 现象 | 含义 | 处置 |
|---|---|---|
| 退出码 `2`，提示「章节号无效」 | 章节号不在模板 95 节点内 | 跑 `check_gate.py --list` 取合法章节号；不得凭记忆猜章节号续写 |
| 退出码 `2`，文件不存在/格式不支持 | 输入资料缺失或不可解析 | 列为补数清单项，改用已有资料继续；**不得用默认值补齐后强行计算** |
| 退出码 `3`，`blocked=true` | 该节点依据已被替代/废止 | **停止写作**。按 `block_reason` 定位须替换的文件 → 核实新依据 → 更新库内 md 的 frontmatter → `rebuild_index.py --rebuild` → `analyze_gaps.py` 复核 → 重跑闸门；闭合前不得产出正文 |
| 脚本崩溃/语法错误 | 环境或脚本缺陷 | 按「无 Python」路径手工执行，并在交付说明中记录该缺陷；不得静默跳过该步骤 |
| 快照过期警告（不阻断） | 索引可能过期 | 先 `rebuild_index.py --rebuild`；未重建则所有输出必须携带「知识库索引可能过期，合规结论未经验证」 |

> 原则：**上述任一路径都必须先告知使用者，再按规则处置**；绝不静默跳过。

## 三、项目数据包（唯一的数据来源）与事实台账

### 3.0 两条喂料路径（按资料形态选，可同时用）

**先判断资料是哪种形态**——选错路径会让数据包近乎全空，下游只能输出占位符：

| 资料形态 | 例子 | 走哪条路 |
|:---|:---|:---|
| **规范化写法**（有「字段名：值」锚点） | 可研表格、占地表、证照、编号文档 | `ingest.py`（确定性抽取） |
| **连续叙述体**（事实散落在长句里） | **既有方案正文**、说明书、设计说明 | `extract_facts.py`（语义抽取） |

**为什么必须分开**：`ingest.py` 按「字段名 + 分隔符 + 值」匹配，写成
「矿区位于河南省新密市超化镇…」的叙述句没有"建设地点："这个锚点，**抽不出来**。
从连续叙述中理解事实是语义任务，不是正则擅长的模式任务。

> **实测教训**：把一份 26 万字的既有方案正文喂给 `ingest.py`，82 个字段中**只有个位数命中**，
> 29 个必填字段全空 —— 写 1.1 节时手里没有任何项目事实，成果必然空洞。
> 换成 `extract_facts.py` 后命中数提升一个量级。

**叙述体路径（三步）**：

```bash
# 1) 资料 → 抽取任务书（交给 AI 助手阅读）
python "$SK\scripts\extract_facts.py" --plan --source 既有方案正文.txt --out 抽取任务书.md

# 2) AI 助手按任务书产出「事实清单.json」后，逐字回溯校验
python "$SK\scripts\extract_facts.py" --check 事实清单.json --source 既有方案正文.txt --out 校验报告.md

# 3) 校验通过后灌入台账（未通过者一律不入台账）
python "$SK\scripts\extract_facts.py" --to-ledger 事实清单.json --source 既有方案正文.txt --ledger 台账.json
```

**第 2 步是本路径的核心防线**（不是走过场）：每条事实的 `evidence_span` 必须能在原文中
**逐字定位**，定位不到即作废。它拦的是 LLM 最危险的行为——「合理但无据」：
资料没写总投资，按同类矿山经验填个"约 3000 万元"，表面可信、极难人工发现。

校验分级 V1~V5（error/warn）见 `rules.json fact_extraction.verification`，
其中 **V1（字段名须属于 82 字段表）与 V2（逐字定位）是 error 级，不通过即作废**；
V3~V5 为 warn，须人工确认后处理。

**共同纪律**：两条路径的产出都进**同一本台账**，冲突由 `ledger.py` 的拒写规则裁决；
两条路径都**只抄不推**，抽不到就留空。

### 3.1 数据包：由原始资料自动抽取，不靠人复述

```bash
python "$SK\scripts\ingest.py" --source 可研报告.docx --source 地勘报告.md --source 占地表.csv --out 数据包.json
```

抽取口径（写在 rules 里，脚本只执行）：
- **字段名（或别名）+ 分隔符 + 数值/文本**；声明单位的字段**必须出现单位**才算命中；
- **单位归一**：公顷/ha→hm²、万方→万m³、摄氏度/°C→℃；
- **冲突判定分级**：**强别名**命中多值 → 标「待人工确认（冲突）」；
  **弱别名**（如「占地面积」之于「工程占地」、「堆高」之于「弃渣场信息」）命中多值 → 只标
  「待人工确认（弱别名多值）」——弱别名一次命中**永不单独构成冲突**，因为同一份资料里
  「占地面积」很可能指弃渣场占地而非工程占地；
- 未命中**不代表资料里没有**，可能只是写法不同——数据包末尾给出「选填未抽到」清单供人工确认。

字段共 **82 个**（13 分区）：项目标识/规模投资/进度/占地/土石方/场地/自然/主体设计（60 个）
＋ 表土资源 / 土壤流失预测 / 水土保持投资 / 防治指标核算（22 个）。
改过 `calc_engine` 后必须跑 `python "$SK\scripts\calc.py" --audit` 确认新输入仍有字段承接。

> **数据包支持三种形态**：`ingest.py` 产出的规范形态、**手写扁平形态**（`{"挖方":"15.2"}`）、
> 列表形态。手写小数据包试算时直接用扁平格式即可（引擎会提示已读入多少字段）。

**声明项目所在省/市**（如"河南省"），否则地方级 Zone A 依据不会激活，闸门只会报全国性依据——
这会漏掉地方强制要求。未声明时闸门会给出 `scope_inactive` 警告。

### 3.2 台账：跨章口径的唯一出口

章节是分次写的，同一事实（防治责任范围面积、防治分区数、执行标准等级、堆置高度……）
会在第 1、2、6、7、9 章反复出现。**台账把「先写下的值」固定下来**，后续章节与台账不符即报警：

```bash
python "$SK\scripts\ledger.py" --file 台账.json --set "防治责任范围面积=86.5" --unit hm² --chapter 1.6.1
python "$SK\scripts\ledger.py" --file 台账.json --show                       # 看全部已定事实
python "$SK\scripts\ledger.py" --file 台账.json --draft 第7章.md --check      # 用稿子反查台账
python "$SK\scripts\ledger.py" --file 台账.json --inject --exclude 7          # 给某章注入他章已定事实
```

规则（`rules.json ledger_rules`）：
- 同一 key 再次登记：值相同 → 一致（放行）；值不同 → **冲突，拒绝写入**，除非显式 `--force`；
- 单位不同 → 单位冲突，拒绝；数值相同单位不同 → 提示而非拒绝；
- 台账**只存在项目工作区**，`ledger.py` 会拒绝写到技能目录或知识库（铁律5）；
- 写入时机：**每个数值第一次被写进正文之前**。写完再补台账，等于事后追认错误。

## 四、计算规则

**必须真算并输出中间量**：规格在 `references/rules.json calc_engine`，执行在 `scripts/calc.py`。
输出「公式 → 代入 → 中间量 → 结果 → 依据」的完整计算书，可直接并入方案相应章节。

```bash
python "$SK\scripts\calc.py" --chapter 7.3.2 --data 数据包.json --ledger 台账.json --out 计算书.md
python "$SK\scripts\calc.py" --list          # 看有哪些计算项、各需要什么输入
python "$SK\scripts\calc.py" --audit         # 自检：每个计算输入是否都有数据包字段承接
```

| 章节 | 计算项 | 算法 | 依据 |
|---|---|---|---|
| `2.3` | 工程占地分类统计勾稽 | 分项之和 = 合计（字段由 rules 声明） | 模板 2.3、GB 50433-2018 附录B 2.3 |
| `2.4` | 土石方（不含表土）平衡勾稽 | 挖方 − 填方 − 弃方 − 建材利用方 − 借方 = 0 | 模板 2.4，须勾稽闭合 |
| `4.4` | 表土平衡 | 剥离/回覆/剩余量（链式代入，可反算） | 模板 4.4.3、GB/T 45107-2024 |
| `6.3` | 土壤流失量预测 | 扰动后−原地貌、措施后−扰动后（差值） | **SL 773-2018** |
| `7.3.2` | 六项防治指标及达标判定 | 逐项机读算式 + 与规范目标值比对 + **反算校核** | **GB/T 50434-2018 表4.0.2-1～8** |
| `8.2` | 监测点位数量与频次 | **只做结构核对，不生成点位数量** | SL/T 277-2024、GB/T 51240-2018 |
| `9.1.2` | 投资估算汇总勾稽 | 各项之和 = 水土保持总投资 | 模板 9.1.2、概（估）算编制规定 |

**参数分两类**（脚本对每个参数都标注来源，不允许含混）：
- **甲类·规范给定**——能从 Zone A 查到的（容许土壤流失量、防治标准等级与目标值、
  六项指标取值口径、弃渣场级别与防洪标准、林草覆盖率取值口径），**自己定，不得问用户**。
  已录：GB/T 50434-2018 表4.0.2-1～8 的 8 区划 × 3 等级 × 2 时段目标值；
  SL 190-2007 表4.1.1 容许土壤流失量。
- **乙类·项目输入**——只能来自数据包或台账。

**算法红线**：
- **缺项目输入就拒绝计算**，输出 `【待填：字段名】` + 「缺数据不可计算」，
  **绝不用默认值、经验值、同类项目值兜底**（这是最隐蔽的编造）；
- **不做凭经验的"拍数"**：8.2 监测点位数量与频次的最小要求未从标准逐字提取前，
  引擎不生成任何点位数量，只做分区覆盖与结构完整性校验；
- **指标口径不得反转**：土壤流失控制比 = 容许土壤流失量 ÷ 治理后土壤流失量（不是反过来）；
- **需行业定额单价的（工程概算单价）只搭结构**，单价必须来自项目资料或定额文件，绝不自拟。
  自拟单价是最容易被评审打回、也是最典型的编造。

## 五、数据缺失时的行为

**缺数据不停笔，但也绝不猜数。** 具体：

1. 缺失字段一律留显式占位符：`【待填：字段名】`
2. 每张表、每个计算标注状态：**可计算** 或 **缺数据不可计算**
3. 章节末尾汇总一张**最小补数清单**：只说缺什么、缺哪个数、影响哪张表
4. 允许先产出结构完整、仅有占位符的章节，待数据补齐后回填重算

## 六、输出格式与写作要求

**完整契约见 `references/package-boilerplate.md`**（每节指令包里的 `_rules_ref` 也指向它）。
**一次读入，全书复用**——不要在每节重复读。要点如下：

**四段式**：正文 → 表格（按 `tables.json` 字段，标可算/不可算）→ 计算过程
（公式→代入→中间量→结果→依据）→ 最小补数清单。

**四条硬要求**（漏一条该节即不合格）：

1. **覆盖全部内容点**：`must_cover` 里 `｜` 前的内容点**逐条不漏**。
2. **落实深度指令**：`｜` 后是「这一条该怎么写」的要求。
   如「空间关系明确到可定位（区/镇/村或桩号）」——只写「本项目位于河南省」不算落实。
   > 覆盖了但写得空泛，C1 过、C5 不过。两者都要满足。
3. **先处理 `conditional_variants`**：条件不成立的按"不涉及的不列"，成立则必须写。
4. **结论不得与 `hard_constraints` 冲突**；冲突时**改结论，不改依据**。

**引用纪律**：

- **Zone B** 附限定语：仅用于写作表达、论证逻辑与案例参考，不得引入与 Zone A 冲突的方法论或参数。
  条目带 `style_role`：优先参照**文体范式**；**方法论**类只给思路、不提供文体。
- **Zone C** 遵守 `references/zone-c-usage.md`：只提取结构信息（不提取结论/参数/专名/数字）；
  与 Zone A 冲突者丢弃并标注「该范例依据的是旧标准，已忽略其合规内容」；
  Zone A 未规定的，必须输出「**Zone A 未明确规定，以下为参考写法，需人工判断**」。

### 表格与排版（**照模板要求**）

### Zone C 写法范式样本（`zss`）——解决"机械感"的关键一层

包内 `zss` 是从 **91 份已批方案正文**抽取的**写法样板**（共 **334 条**），已强制脱敏
（数值/项目名/地名/单位名/文号全替换为 `〔数值〕`〔市〕等）。它给的是
"**这一段别人怎么起笔、怎么详略、怎么收口**"，不是"写了什么"。

三条纪律（详见 `package-boilerplate.md`）：

1. **只借写法，不借内容**——`〔数值〕` 必须用本项目数据替换，不得照抄原范例任何数字；
2. **模板与 Zone A 优先**——样本只是加法，不改变"该写什么"；
3. **不得直接用于新项目**——不得因其"曾经通过"而推定做法在当前标准下仍合规。

> **样本已按节点号轮转选取**：不同节点拿到不同范文，避免全书反复看到同一条。
> 生成与自检：`python "$SK\scripts\extract_style_samples.py" --build` / `--audit` / `--show <主题>`。

### 去机械感——把"像人写的"变成可执行的动作

上面 `zss` 解决的是"**看到什么好写法**"，这一节解决"**写的时候具体怎么做**"。
判据全部来自 Zone C 91 份已批方案的实测统计（1471 万字 / 5.07 万句），
规则在 `rules.json human_voice`，执行在 `scripts/check_draft.py`（C5 层的独立一支）。

> **一句话原理**：机器文本的破绽不是"用错了词"，而是**过于均匀**——
> 句长均匀、起笔雷同、收口同调。所以下面六条针对的都是"离散度"，不是"用词表"。

#### 六条可执行的动作

| # | 动作 | 判据（实测） |
|---|---|---|
| 1 | **起笔轮转** | 段落开头别老用同一个词。真人间 2 字最高占比中位 **25%**，上限 50%。在「陈述（本项目…）／判断（该区…）／条件（鉴于…）／指代（其中…）／时空（施工期…）」之间换着来。 |
| 2 | **标点要"像中文"** | 真人每千字：逗号 **32.7**、句号 **13.7**、顿号 **13.2**、分号 **2.5**、括号 **4.6**、破折号 **0.0**。<br>**破折号（——）在正式方案里基本不用**，全文出现超 1.7‰ 即报滥用——这是 AI 文本最典型的标点特征，务必克制。 |
| 3 | **长短句交错** | 真人句长标准差中位 **60.3**，短句（≤25 字）占 **27%**。<br>不要全篇都是 40~70 字的句子——**每段至少放一个短句**，让节奏有停顿。 |
| 4 | **连接词克制** | 真人连接词密度中位 **0.48‰**、P90 为 **2.09‰**。<br>**「首先/其次/再次/最后」一律不用**（真人几乎不出现）；「同时/因此/此外/综上/值得注意的是」别堆叠。 |
| 5 | **收口不要复述** | 不要每节结尾都把内容点重说一遍，**禁用**「综上所述／总而言之／由此可见」收尾。真要收口，就给一个**具体判断或数字**。 |
| 6 | **别套同一骨架** | 同一句式（如「通过…，实现…」「在…方面」「既…又…」）单节内出现 ≥4 次即报「句式同构」。换主谓宾、换切入点。 |

#### 写法示范（同一句话的两种写法）

```text
✗ 机械：首先，本项目需要重视水土保持工作。其次，本项目需要采取工程措施。
       通过分析项目区地形条件，确定了防治分区。通过分析项目区气候条件，确定了防治标准。
       综上所述，本项目的方案是可行的。

✓ 人写：项目区属低山丘陵，地形起伏大，施工期扰动集中——这是本方案分区防治的主要依据。
       按地貌与施工时序，全区分两个防治分区；Ⅰ区以工程措施为主，Ⅱ区配合植物措施。
       经核算，防治责任范围 15.32 hm²，林草覆盖率目标 27.5%，均满足规范要求。
```

差别不在"用了什么高级词"，而在：**有短句、有破折号以外的停顿、有具体数字收口、不套骨架**。

#### 怎么写完之后自查

```bash
python "$SK\scripts\check_draft.py" --draft 第7章.md --chapter 7 --province 河南省
```

C5 会列出「去机械感」提示。**这些都是 warning，不阻断交付**——
人味是风格判断，做成硬阻断会误杀正常稿子；
但一条都不提示，机械感就永远没人管。**看到提示就改，改完再跑一次。**

#### ⚠ 改稿前必做：先冻结事实

为句子齐整而改数字、措辞、关系，会**读着顺了、方案已经错了**。**只动承载方式，
不动承载的事实**——必冻结 6 类（数字/文号/指标/专名/条款原文/关系词），
改完逐句回指、**对不上就回退**。清单见 `references/de-mechanize.md`。

> **标定说明（为什么阈值长这样）**：初版凭直觉把逗号上限定成 12‰（真实中位 32.7‰），
> 结果 8 份**真实已批方案每份都误报**；连接词上限 0.5‰ 更是正好压在真人中位数上，
> 等于把一半合格稿子判成机器腔。现在所有阈值都按真实分位数取 P90/P95，
> 实测真实方案平均仅 0.4 条提示（8 份中 6 份完全干净），而典型机器腔文本 5 条全中。

## 七、篇幅与深度控制（全书 150–180 页）

一本方案通常 150–180 页。**写太少不够、太多溢出，所以每写一节都要实时对照预算**——
不能等写完全书再看总长度。规则在 `rules.json length_budget`，执行在 `scripts/budget.py`。

**折算口径**：正文目标 **123,750 字** ＝ 165 页（150–180 的中间值）× 1000 字/页 ×（1 − 0.25 开销）
（0.25 ＝ 表格、公式、图注等非正文版面占比，即正文约占整书版面 75%；差额 41,250 字就是这些版面。

**分配方式**：两步分配，都写在 rules 里，不靠感觉——
1. **章间**按 `chapter_shares` 分配：**由 Zone C 72 份可用范例实测的章篇幅占比中位数**得出
   （老 1 章 9.0% / 老 2 章 32.4% / 老 3 章 11.7% / … / 老 8 章 2.7%），
   再经老八章 → 2026 版 10 章映射（老 1↔新 1、2↔2、3↔3、6↔4、7↔5、8↔6、9↔7、10↔8；
   新增的 4/5 章按模板权重分摊后归一）。**只借"哪一章通常写多少"这一分布特征，不借其内容。**
   这一步解决的是"前松后紧"：按模板节点数平均分配会让第 2 章（项目概况）严重虚胖、
   第 7 章（水土保持防治，全书技术核心）严重不足。
2. **章内**按节点权重（`node_level_weights`：一级节点 0.7 / 二级 1.0 / 三级 0.6）。

**每个节点都有三项预算**：`目标字数`、`下限`、`上限`（＝目标 × 容差 0.8 / 1.25）。
写一节就查一节：

```bash
python "$SK\scripts\budget.py" --chapter 7        # 看第 7 章逐节预算
python "$SK\scripts\budget.py" --count 第7章.md   # 统计实际字数并逐节判定（偏少/达标/超标）
python "$SK\scripts\budget.py" --count 全书.md --progress   # 全书进度与页数折算
```

**判定与动作**（`check_draft.py` C6 / `check_plan.py` 第五节自动给）：

| 判定 | 含义 | 动作 |
|---|---|---|
| 偏少（< 下限） | 内容点写完了但深度不够 | 补**深度要素**：依据引用、量化数据、结论句、机理说明，不是补空话 |
| 达标 | 区间内 | 通过 |
| 超标（> 上限） | 占了别节的篇幅 | 压缩重复论述、把清单式罗列改表格、合并同义段 |

**深度要素**（`rules.json style_rules.depth_patterns`，逐节检查而非全局平均）：
`依据引用`（引到具体标准/条款）、`量化数据`（数+单位）、`结论句`（"因此/说明/应…"）、
`机理说明`（"由于/导致/为了防止…"）。四种要素**缺哪种补哪种**，这是"写够字数"与
"写够深度"的区别——前者靠废话，后者靠要素。

## 八、七类知识资产（写一节时装配什么）

模板 420 个内容点归纳起来只需 **7 类知识资产**。前 4 类由三层知识库提供，
后 3 类是**从知识库加工出来的结构化索引**：

| # | 资产 | 服务什么 | 来源 | 载体 | 条目数 |
|:--:|:---|:---|:---|:---|:--:|
| **A** | 规范依据 | "依据是什么" | Zone A | `zone-a-index.json` | 75 |
| **B** | 事实台账 | "本项目的值是多少" | 项目资料 | `台账.json` | 82 字段 |
| **C** | 写法范式 | "这段话该怎么写" | Zone C 正文 | `zone_c_style_samples.json` | 334 |
| **D** | 物种名录 | "该种什么树、什么草" | Zone B 专著 | `species_index.json` | **87** |
| **E** | 参数口径 | "这个参数取多少" | Zone A 标准表 | `design_params.json` | **8 组** |
| **F** | 工法索引 | "这个措施怎么做" | Zone A 条文 | `measure_methods.json` | **33** |
| **G** | 文体范式 | "哪些资料可参照写法" | Zone B | `zone-b-index.json` 的 `style_role` | — |

**写一节时的装配结果**（以 7.7 分区措施布设为例）：

```
Zone A 硬约束      → 该写什么、不得违反什么
事实台账           → 本项目的值
Zone C 范例 + 样本 → 有哪几份可参照 / 这一段怎么写
Zone B 文体范式    → 写法样板（优先"文体范式"类）
【D】物种          → 这里种什么树什么草、习性如何
【E】参数          → 这个数该取多少、依据哪条标准表
【F】工法          → 这个措施怎么做、设计要求是什么
```

> **三层各司其职**：Zone A 定红线，Zone B 给写法，Zone C 给范式。
> D/E/F 是把三层知识**加工成可调用形态**的索引——它们不新增知识，
> 只是让原本埋在数万字正文里的内容在写作时能被自动取到。
> **完整能力清单见 `references/capability-index.md`**（含 13 项不变量断言，
> 由 `python "$SK\_meta\build_capability_index.py" --check` 核对）。

**叙述型章节**（`rules.json zone_c_injection.narrative_nodes`：第 1 章各节、1.9、2.1、10.1、10.2）
即使有 Zone A 专属依据也会开启 Zone C 文体参考——这类章节的质量瓶颈是**缺文体参照**，
不是缺依据。计算型/评价型章节（如 7.3.2、2.4、9.1.2）仍走原闸门，避免范例结论污染指标判定。

## 九、交付标准（Word 文件）

**方案一律以 Word 文件为交付物，不另在文件之外输出正文内容。**

| 情形 | 交付方式 |
|:---|:---|
| **已有 Word 文件**（在已有 Word 文件或新建 Word 文件中写作改动） | **直接把方案写入该 Word 文件**，不在文件之外另行输出内容 |
| **没有已有 Word 文件**（需直接撰写方案） | **交付一个 Word 文件**（文件命名、存放路径等待补充：…） |

**四条固定动作**：

1. **文件位置**——Word 文件**直接创建在工作区相应文件夹内**。
2. **必须报告存储路径**——交付时明确给出 Word 文件的完整存储路径，不得只报文件名。
3. **文件命名必须带日期**，如 `2026.09.16`。
4. **写完后自动打开该 Word 文件**——两种情形都适用。

> **排版规格不因交付方式改变**：字体、字号、页眉页脚、封面、责任页、目录等一律照
> `references/table-format.md`（`办水保函〔2026〕232号-附件2` 逐字）执行。

## 十一、第一次上手：照着走一遍

**不要靠读示例学**——示例会过时，而脚本永远给当前真实结果。直接跑：

```bash
# 1) 看某节到底要什么（闸门 + 骨架 + 内容点 + 硬约束 + 资产 + 篇幅预算，一次给全）
python "$SK\scripts\write_chapter.py" --chapter 1.1 --province 河南省 --out 指令包.json

# 2) 算数（缺数据会明确告诉你缺什么，不会猜）
python "$SK\scripts\calc.py" --chapter 7.3.2 --data 数据包.json --out 计算书.md

# 3) 写完一节立刻回检（不要等全书）
python "$SK\scripts\check_draft.py" --draft 稿件.md --chapter 1.6.2 --province 河南省 --ledger 台账.json
```

指令包里的键名是**短名**（为省 token），对照见 `references/key-alias.md`。
`must_cover` 用 `｜` 分隔"内容点｜深度指令"，两者都要满足。

**若闸门返回 `blocked=true`**：不得产出任何正文，只输出阻断原因与解决路径
（如"库中相关依据已被替代，须替换为 X"）。
