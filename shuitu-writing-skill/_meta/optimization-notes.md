## 一、优化前基线（2026-05 实测）

| 口径 | 现状 |
|:---|:---|
| **L0 常驻**（每次加载技能） | SKILL.md 45.0 KB / 743 行 ≈ **11,359 token** |
| **L1 单节指令包** | 均值 35.9 KB ≈ **9,065 token**；最大 7.7 节 ≈ **16,667 token** |

**问题**：写完一本方案，光"取指令"就要烧掉 86 万 token。用户的痛感正来自这里。

## 二、根因分析（四个浪费点，全部实测）

| # | 浪费点 | 实测证据 |
|:--|:---|:---|
| 1 | **`hard_constraints[].requirement` 整段贴原文** | 9.1.2 节 22 条约束里 requirement 占 26.9%；单条最长 1,400+ 字符（把整份《审查要点》通知贴进一条） |
| 2 | **`data_requirements` 与 `nodes.required_content_points` 内容重复** | 只多了 `chapter_id`/`data_class`/`classified_by` 三个壳字段 |
| 3 | **检索期元数据全程携带** | `source_file`（完整 md 路径）7.7 节占 1928 字符；`match_score`/`status`/`origin` 写作期完全不用 |
| 4 | **固定样板每节重复** | `_rules`/`output_format`/各 `*_qualifier` 共 913 字符，逐节原样推 |

**第 5 个（最大，一开始没看出来）**：`required_content_points` 与 `writing_directive`
**同序一一对应**，而 `writing_directive` 每条把内容点**再抄一遍**、还把模板原句**又抄一遍**：

```
rcp[3] = 项目位置
wd[3]  = 说明「项目位置」：空间关系明确到可定位（区/镇/村或桩号）（模板原句：「简述项目位置」）
```

净信息只有「动词 + 深度要求」，字符却涨 3~4 倍。1.1 节实测 rcp 622 + wd 2481 = 3103 字符。

## 三、优化措施与实测收益

| 措施 | 做法 | 实测收益 |
|:---|:---|:---|
| ① **键名速记** | 长键→短键；对照表**移出包外**到 `references/key-alias.md` | 见下方坑 1、2 |
| ② **超长条款截断** | `requirement` 优先提取**首个规范句**（含应/宜/不得），否则截 200 字符 + `more` + `oi` 指针 | 9.1.2 的 hc 从 10,839 → 6,000 字符级 |
| ③ **源文件归一** | `source_file` + `source` 合成引用表 `g.src_files`，条目只留 `s` 索引 | 7.7 节省 3,006 字符 |
| ④ **内容点合并** | `rcp` + `wd` 合并为 `"内容点｜动词·深度"`，模板原句整包只留一份 | 1.1 节 3,103 → ~1,200 字符 |
| ⑤ **去掉可推算字段** | `target_raw`/`share`/`chapter_share`/`weight` 等由 `target` 可推算者删除 | 2.4 节 lb 从 31% → 见坑 3 |
| ⑥ **资产去噪** | `measure_methods` 剔除措施名为空/名称其实是标准名的噪音条目 | 7.7 节剔除 3 条 ≈ 700 字符 |
| ⑦ **Zone B 多样性选取** | 按节点号确定性轮转，相邻节不再拿同一批素材 | 重复率 87%→79%，最高重复 45→38 次 |
| ⑦b **Zone C 样本多样性** | 同理（**第一轮曾漏掉这块**） | 重复率 67%→47%，最高重复 14→5 次 |
| ⑧ **SKILL.md 瘦身** | 主文件只留"执行必须知道"的；知识库分区/时效性/入赅流程/文件树/示例外移 | 常驻 11,359 → **7,721 token** |
| ⑨ **固定样板外移** | `_rules` + `output_format` 逐字固定却逐节重复 → 移入 `package-boilerplate.md` | 省全书约 **6.9%** |
| ⑩ **硬编码阈值入 rules** | `REQ_KEEP`/`_ABBREV_MIN_CHARS`/`ASSET_TEXT_KEEP` → `rules.json compact_pack` | 遵守"规则不得只写在代码里" |

**综合结果（全书 95 节点实测）**：

| 口径 | 优化前 | 优化后 | 降幅 |
|:---|---:|---:|---:|
| **常驻**（SKILL.md） | 11,359 token | **7,721 token** | 32.0% |
| **全书 95 节指令包** | 861,252 token | **463,037 token** | **46.2%** |
| 均值/节 | 9,065 token | **4,874 token** | 46.2% |
| 指令包总体积 | ~4.9 MB | **1.87 MB** | 62% |

**全书总消耗：872,611 → 470,758 token（省 46.1%）**

## 四、踩过的坑（重要，勿重复）

### 坑 1：包内塞完整对照表 = 白交税

第一版把 200+ 条 `KEY_ALIAS` 整个塞进包里当 `ct`，
**ct 自身 3,307 字符**，把缩写省下的 token 又吃回去，净收益≈0。

**结论**：对照表必须**移出包外**（`references/key-alias.md`，一次读入全书复用）。

### 坑 2：包内塞「本包用到的」对照表 = 仍在交税

第二版改为只列本包实际用到的键，ct 降到 1,632~1,789 字符，
**仍占包体 7~10.5%**。包越大税越重。

**结论**：任何形式的包内对照表都是固定税 → 彻底移出，包内只留一行指针。

### 坑 3：`lb` 下有**两处**节点列表，只过滤了一处

`length_budget` 同时有 `nodes`（本节点）与 `chapter.nodes`（整章全节点）。
早先只过滤了前者，导致 **2.4 节的 lb 仍占 30.9%**。

**结论**：改结构时先 `json.dumps` 打印实际层级，别凭记忆以为只有一处。

### 坑 4：中文字段名绕过压缩

`species_index.json` / `measure_methods.json` 用的是**中文字段名**（措施/依据/设计要求/名称/学名/生态习性），
而 `KEY_ALIAS` 一开始只有英文键 → 这两块（合计 12.8 KB，包内最大）**既没被缩写也没被截断**，
压缩率卡在 5% 左右上不去。

**结论**：建别名表前先枚举**实际出现的键名**（`_collect_keys`），别假定都是英文。

### 坑 5：`_dedup_meta` 用了短键名，静默失效

`_dedup_meta` 在**别名替换之前**执行，却写成读 `rec.get('sf')`/`rec.get('ms')`，
而那时键还是长的 `source_file`/`match_score` → 去除逻辑**一条都没生效**（实测 `st`/`ms`/`og`/`sc` 全还在包里）。

**结论**：压缩流水线里，**每个函数都要写明它工作在哪一阶段**（别名前/后），否则静默失效。

### 坑 6：`max_items` 砍条目 = 漏知识点

给 `species_references` 设 `max_items=20`、`measure_methods=16` 后，
7.7 节的物种 30→21、工法 21→16 —— **真的丢了条目**。

**结论**：与"不漏任何知识点"直接冲突。省 token 必须靠**截断长文本**，
**不能砍条目**（条目名本身就是"该种什么树草/有哪些措施"的完整清单）。
上限应设为远高于实际条数的防病态值。

### 坑 7（最严重）：数据包格式不兼容 → 给了数却算不出来

`calc.py` 的 `Inputs` 只认 `ingest.py` 产出的规范形态
`{"fields": {"挖方": {"value": …}}}`。
把最自然的**扁平形态** `{"挖方": "15.2"}` 喂进去时，引擎报
**「数据包/台账中无此字段」——数明明给了，却算不出来**。

这个 bug 的危害不只是"算不出来"：
它会**误导使用者以为字段缺失**，进而"补个默认值"，正好踩中本技能最严的禁止项（编造数据）。

**修复**：`_load_package()` 同时支持三种形态（规范 dict / 扁平映射 / 列表），
并显式提示"扁平格式已读入 N 个字段"。

**结论**：**引擎的输入宽容度应该高于产出格式**。
下游工具不能只认自己家上游的产出格式——使用者手写一个小数据包试算，是最常见的用法。

### 坑 8（送审级后果）：容差语义混淆 → 真实的不闭合被放过

`sum_check`（工程占地分类统计）与 `balance_check`（土石方平衡）**共用了 `tolerance: 0.01`**。
对土石方平衡，0.01 作相对容差合理（万m³ 级量的凑整误差）；
对分类统计，它意味着 **86.5 hm² 的容差 = 0.865**，于是：

```
永久占地 50 + 临时占地 36.6 = 86.6  ≠  工程占地 86.5   →  却判「勾稽闭合」
```

差 0.1 hm² 被放过，差 0.8 hm² 也会被放过。**这正是评审最容易挑出来的错，却查不出来。**

**修复**：
- `sum_check` 改用**绝对容差**（默认 1e-6，浮点精度级）+ 相对容差 0；
- 容差语义**写进 rules.json**（`calc_engine.tolerance_semantics`），不留在代码里（遵守"规则不得只写在代码里"）；
- 项目若有明确凑整惯例，须**显式**声明 `tolerance_abs`，不得靠放宽默认值解决。

**结论**：**"定义式恒等"与"工程平衡"的容差语义不同，绝不能共用一个相对容差。**
凡是共用同一个容差参数的地方，都要问一句"这两处的容差含义真的一样吗"。

### 坑 9：Zone B 素材被重复注入 45 次

原排序只看 `relevance`/`style_role`，与"本节"无关，
于是每节的 Top-6 几乎是同一批书。实测全书 95 节共注入 **469 条，去重后仅 61 个文件**
（重复率 87%），《大型线性工程水土保持方案编制要点研究》**被注入 45 次**。

**修复**：`_diversify()` 按节点号做**确定性轮转**（同精度、同 style_role 组内轮转，
不跨组以保住质量规则）。用节点号做种子而非随机数，保证同一节点每次出包结果一致（可复现）。
实测去重率 13% → **65%**，最高重复 45 次 → **5 次**。

**结论**：**"每节都取 Top-N"等于每节都取同一批 N。**
多节流水线场景下，选取策略必须带**多样性**，否则重复内容会线性放大 token 成本。

### 坑 10：验证脚本硬编码短键名 → 自己误报

`verify_equiv.py` 里写死 `x.get('pts')` 统计数据需求条数。
后来 KEY_ALIAS 把 `pts` 改名为 `pts_`，计数就变成 0，
脚本**误报"压缩丢信息"**——而数据其实一条没少。

**修复**：改为「候选键名列表 + 兜底取第一个 list 值」。

**结论**：**验证脚本必须对被测对象的实现细节免疫**，
否则会产生"狼来了"——真丢信息时反而没人信。同理，`ct_note` 里的键名也从
KEY_ALIAS 反查生成，不写字面量（早先手写 `hc[].s`/`hc[].oi`，别名一改就脱节）。

### 坑 11（影响所有真实稿件）：子标题把正文"抢走"，字数统计全错

**这是最该早发现、却拖到第二轮迭代才发现的一个**——
因为前两轮自检只验证"脚本能不能跑、逻辑对不对"，
**从没真正写一节正文去撞它**。

实测：写一节正常稿件（带 `## 一、正文` / `### （一）xxx` 子标题）后，

```
split_by_node 结果: {'1.6.2': 0, '7.2': 76, '1.6': 1409}
```

**本节字数为 0**、篇幅判定「偏少 -100%」、1084 字被归入"未归入任何节点"。

两个叠加的根因：

1. **子标题切断归属**：原实现按「下一个标题」切段，而 `## 一、正文` 这类子标题
   识别不出节点号（cid 为空），其正文全部归到 `''`。
   多级子标题是**正常且推荐的写法**（四段式本身就带子标题），
   所以这个 bug 会让**绝大多数真实稿件**统计失真。

2. **中文序号被误判成节点号**：标题逐字匹配（拿模板标题去标题行里找子串）
   这个**危险回退**把 `（二）水土流失防治分区` 匹配成了 `1.6`、
   `（一）方案设计水平年` 匹配成了 `7.2`——因为某节点标题恰好含这些字样。

**修复**：
- 子标题**继承最近一个可识别节点**，不再切断归属；
- 节点号必须是**独立 token**（前后不能紧邻数字或小数点）；
- 优先匹配**标题开头**的节点号；标题逐字匹配**只在不含中文序号时**才允许。

**结论（三条，以后照办）**：

1. **必须实写一节正文来验收**——等价性、自检、对抗性检查都只验证"包和逻辑"，
   验证不了"用起来对不对"。这个 bug 只有真写一段带子标题的正文才会暴露。
2. **凡是"逐字匹配模板文字"的回退逻辑都要加闸**——模板标题是短名词，
   极易作为子串命中写作者的正常子标题。
3. **中文序号（一、二、三…）与节点号必须在词法上区分开**，
   否则 `（二）` 这种再普通不过的写法就会引发误判。

### 坑 12：外部 import 会在技能目录留 `__pycache__`

模块里写 `sys.dont_write_bytecode = True` **来不及生效**——
Python 在 import 时**先编译写盘、后执行模块体**，所以这条语句管不住自己的 `.pyc`。
只有调用方加 `-B` 或设 `PYTHONDONTWRITEBYTECODE=1` 才可靠。

**处置**：自检改为「用 `-B` 跑一遍确认无残留」并**统一清理历史残留**；
文档中明确这一点。不再把"使用者不带 `-B` 的外部 import"当作技能缺陷。

**结论**：**"技能目录零残留"不能只靠模块内自设**，
要么入口脚本统一设置，要么事后清理——两者至少要有一个。

### 坑 13：省 token 的两项措施会互相干扰

`_diversify`（Zone B 多样性）按 `(relevance, style_role)` 分组轮转，
而我做的"去元数据壳"压缩会**删掉 `relevance`**。
好在 `_diversify` 在压缩**之前**执行，分组仍正确——
但这说明：**压缩流水线的每一步都要确认它作用于哪个阶段**，
否则两个都"正确"的优化叠加起来会产生错误结果。

**结论**：多个省 token 措施叠加时，必须验证**组合效果**，
不能只逐个验证（坑 5 的 `_dedup_meta` 静默失效是同类问题的另一种形态）。

## 五、能力保障（省 token 不能省能力）

压缩全程遵守三条：

1. **只删重复，不删信息**：同样内容只留一处，被删处留指针。
2. **截断必留回溯链**：超长文本截断后附 `more`（原文长度）+ `oi`（序号），
   配合 `g.src_files[s-1]` 可唯一定位原文。
3. **可逆**：`--full` 一键还原完整包。

**等价性验证**（`_meta/verify_equiv.py`）：压缩前后逐项核对
`hc 条数 / 节点数 / 内容点数 / 指令条数 / Zone B/C 条数 / 样本数 / 物种数 / 工法数 / 参数组数`
——**全部一致**才允许合入。

## 六、知识库随技能包交付（vault 内嵌）

**变更**：原先知识库是外部的 Obsidian 库（硬编码绝对路径
`<OBSIDIAN_VAULT>`），现**随技能包交付**。

**最终结构**：

```
<技能包>/
├── SKILL.md
├── README.md
├── references/          ← 索引快照与规范文件（48.4 MB，其中 search_index.kbx 41.5 MB）
├── scripts/             ← 28 个脚本（另有 _meta/ 10 个，合计 38 个）
├── _meta/               ← 验收工具与本记录
├── .cache/              ← KBX 解析缓存（可安全删除，会自动重建）
└── vault/               ← 知识库（503.0 MB）
    ├── md库/            ← 371 个 md
    │   ├── Zone A - 规范层/     (75)
    │   ├── Zone B - 参考层/     (204)
    │   └── Zone C - 应用范例/   (91)
    └── .obsidian/       ← Obsidian 配置（可直接打开 vault/ 编辑）
```

技能代码部分仅 **11.2 MB**，知识库 **566.5 MB** 完全隔离在 `vault/`。

**路径解析**：集中在 `scripts/vault_paths.py`（唯一入口）。
优先级：`DSH_WS_VAULT` 环境变量 → `<技能包>/vault/` → `<技能包>/`。

### 踩过的坑（本轮新增）

#### 坑 14：库根选错，把技能自身的 md 当成了知识库条目

最初把 `md库` 直接放在技能包根，并让 `resolve()` 返回技能包根。
`rebuild_index.py` 从库根**递归扫描**，于是把 `SKILL.md`、`README.md`、
`references/*.md` 一并算作知识库条目——实测"库内 md 文件: 386"（实际 371），
凭空多出 15 条，并触发快照漂移告警。

**修复**：知识库放进 `<技能包>/vault/`，库根指向 `vault/`，
技能自身文档与知识库天然隔离。

**结论**：**"库根"与"项目根"是两回事。**
凡是从某个根目录**递归扫描**的工具，都要确认这个根里没有不该扫的东西。

#### 坑 15：7 处硬编码路径，漏改一处不报错

原先 7 个脚本各写一份绝对路径。漏改的那处**不会报错**——
它会静默地把知识库当成"不可达"，输出过期警告或返回空依据。
这比崩溃危险得多：使用者看到的是"功能正常"，只是结果不对。

**修复**：全部改为 `from vault_paths import VAULT`，
路径规则**只在一个文件里定义一次**。

**结论**：**同一份配置在多处重复，是"静默失效"的温床。**
发现重复立刻收敛到单一入口。

#### 坑 16：环境变量指错时"静默回退"更危险

若 `DSH_WS_VAULT` 指向无效路径却回退到技能包内库，
使用者会以为"换库成功了"，实际读的仍是旧库。

**修复**：`is_ready()` / `unavailable_reason()`，
`kb_lookup --map` 在库不可用时输出 `⚠ 知识库不可达` 并说明原因，
**明确不回退**。

**结论**：**配置错误要"响亮地失败"，不要"安静地降级"。**

#### 坑 17：`vault_paths` 自身会留下 `.pyc`（Python import 时序）

所有脚本都设了 `sys.dont_write_bytecode = True`，
但新引入的 `vault_paths` 是**被依赖的最底层模块**，
它自己的 `.pyc` 在模块体执行前就已写盘——模块内的设置管不住自己。

**修复**：在 `vault_paths` 加载完成时**当次自清**自己的 `.pyc`
（`_clean_own_bytecode()`），并删空目录。实测三种调用方式均零残留。

**结论**：**"零残留"要靠知道自己何时被写盘**——
被依赖的最底层模块必须能自我清理，不能只依赖调用方。

#### 坑 18：删副本前必须**逐文件哈希比对**，不能只看文件数

迁库后要删掉 E 盘原副本。**371 个文件、数量与体积完全一致**，
看起来可以直接删。实际逐文件 SHA256 比对发现：

| 项 | 结果 |
|:---|:---|
| 文件数 | 371 = 371 ✅ |
| 总体积 | 566.44 MB = 566.44 MB ✅ |
| **逐文件哈希** | **370 一致，1 个不同** ❌ |

差异文件 `水土保持工程概算定额（2025年版）.md`：
**文本内容一字不差（4706 行，diff 差异块 0）**，但字节不同——

- E 盘：LF（`\n`），968,496 字节，修改于 09-15 11:00
- 包内：CRLF（`\r\n`），973,201 字节，修改于 09-15 00:21

**E 盘那份在我拷贝之后被外部改过**（时间戳晚 10.5 小时）。
若只看"N 个文件、体积一致"就删，这一处改动会被永久丢失。

**处置**：按用户选择统一为 LF（二进制精确替换，只动 `\r\n`→`\n`），
复算哈希与 E 盘完全一致后才删除。删后重跑全部验收，8 项全过。

**结论（三条）**：

1. **"文件数 + 总体积一致"不等于"内容一致"**——
   换行符、BOM、编码都能让体积几乎不变而内容有差。
2. **删除前必做逐文件哈希比对**，且要比对**源与目标**，
   不能只验目标端"看起来齐全"。
3. **留意时间戳**：目标文件的修改时间**晚于**拷贝时间，
   说明期间被改过，必须查明原因再决定保留哪版。

#### 坑 19：`--ask` 查不到文件，其实是"查错地方了"

删除后验证时 `kb_lookup.py --ask 概算定额` 报「索引中未找到」，
一度以为是迁库导致的索引缺失。实际：

- 该文件**在** `zone-a-index.json` 里（`水土保持工程概算定额`）；
- `--ask` 设计上**只查三类加工资产**（物种 / 设计参数 / 措施工法），
  **不查规范文件本身**；找文件应走 `--ask-a` 或 `--chapter`。

**不是 bug，但原提示词有误导**——它只说"未找到"，
使用者会以为"库里没有这份文件"。已改为明确区分：

```
在**加工资产**（物种 / 设计参数 / 措施工法）中未找到「X」。
注意 --ask 只查这三类加工资产，**不查规范文件本身**。若你要找的是：
  · 某份规范/标准/文件   → `--ask-a`
  · 某章节该用哪些依据   → `--chapter <节点>`
  · 某条规范里的具体条款 → 先用 `--ask-a` 定位文件，再只读那一份
  · 写法样例             → `--ask-style <主题>`
```

**结论**：**"查不到"的提示要能区分「确实没有」与「你查错入口了」**，
否则使用者会基于错误结论去"补资料"。

### 9.3 去机械感：把"像人写的"做成可回归的判据

新增 `rules.json human_voice` 规则组（六项）+ `check_draft.py` 的
`human_voice_check()`，并入 C5 输出（全部 `warning`，不阻断交付）。

**原理**：机器文本的破绽不是"用错词"，而是**过于均匀**——
句长均匀、起笔雷同、收口同调。所以判据针对**离散度**，不是词表。

**阈值全部实测标定**（Zone C 91 份已批方案、1471 万字 / 5.07 万句、1521 个 3000 字窗口）：

| 指标 | 真人实测 | 取用阈值 |
|:--|:--|:--|
| 逗号密度 | 中位 **32.7‰**（P05 12.4 / P95 50.2） | 12~50‰ |
| 句长标准差 | 中位 **60.3**（P05 9.2） | ≥9 |
| 短句（≤25 字）占比 | 中位 **27%**（P05 8%） | ≥8% |
| 连接词密度 | 中位 **0.48‰**（P90 2.09） | ≤2.1‰ |
| 段落前 2 字最高占比 | 中位 **25%**（P95 56%） | ≤50% |
| 破折号 | 中位 **0‰** | ≤1.7‰ |

> **坑 14（阈值按"整篇"标定，实际按"单节"运行 → 全线误报）**：
> 初版凭直觉把逗号上限定成 **12‰**，而真人单节中位是 **32.7‰**——
> 结果 8 份**真实已批方案每份都报「标点过密」**；
> 连接词上限 **0.5‰** 更是正压在真人中位数 **0.48‰** 上，
> 等于把一半合格稿判成机器腔。
> **教训**：阈值必须在**与运行同尺度**的样本上标定。整篇统计与单节统计差近 3 倍，
> 用整篇数据定单节阈值，规则上线即失效——使用者会很快把整个体检关掉，那比不做还糟。

> **坑 15（正则跨行匹配，凭空造出假骨架）**：句式骨架正则用 `[^，。]`，
> 字符类**允许换行**，于是 `"为公共管理与公共服务\n用地（教育用地），…"`
> 被当成「为…，…」骨架，单个节点凭空多出 17 处命中。
> 修复：`[^，。\n]`，骨架必须在同一行内闭合。
> 同时 **「根据…，…」「为…，…」不得作为同构判据**——前者是公文正当写法
> （"根据地勘报告…"），后者「为」兼作系动词（"为学校项目，属于公益性工程"），
> 实测 17 命中全是正常句。只保留机器明显偏好的对偶堆叠式骨架。

> **坑 16（统计把非行文内容也算进去）**：初版对真实方案跑出**每份都报标点异常**，
> 逐层排查出三类污染源：① **点线目录**（`1.1 项目简况...  ....5`）；
> ② **LaTeX 公式**（`$$ M_{yz}=RKL_yS_yBETA $$`，几乎无中文标点，
> 把密度压到 6‰ 以下 → 误报「标点偏少」）；③ 纯页码/表格分隔线。
> 新增 `_strip_non_prose()` 统一剔除，并按**样本量**设门槛
> （≥1500 字且 ≥20 句才判标点，否则样本不足不发言）。

## 十、2026-09 第二轮：Skill 索引误判专项排查与修复

### 10.1 背景与目标

用户要求「再次检查 skill 索引误判的问题，务必把全部问题抓出来修复」。本轮**不靠读代码
猜问题**，而是建立"全库真值"做**对抗性比对**：直接流式扫描 371 个文件取真实命中，
再与索引返回结果逐词对比，凡不一致即为误判。

### 10.2 抓出的三个真问题（均有量化证据）

#### 问题 1（最严重）：高频词截断吃掉文件覆盖

`build_search_index.py` 旧实现：

```python
final[term] = postings[:max_postings]   # max_postings = 400
```

注释写的是"只保留前 N 个**文件**"，但代码是"取文档序前 400 **处**"。
热门词的前 400 处集中在最靠前的几个文件里，于是：

| 词 | 索引文件数 | 真值文件数 | 覆盖率 |
|---|---|---|---|
| 保持 | 10 | 348 | **2.9%** |
| 防治 | 4 | 305 | **1.3%** |
| 水土 | 8 | 344 | **2.3%** |
| 表土 | 42 | 251 | 16.7% |

**最危险的是它完全静默**：查询照常返回几十条结果，使用者根本不知道
自己只看到了 2% 的资料。7,172 个词条受此影响。

**修法**：先按文件聚合，再**轮转（round-robin）分配行预算**——
每轮每个文件取 1 行，直到用满 400 处；另设 `MAX_LINES_PER_FILE = 8`
防止单文件垄断。效果（构造用例：1 个文件 400 行 + 300 个文件各 1 行）：

```
旧算法: 400 处, 覆盖   1 文件
新算法: 308 处, 覆盖 301 文件
```

实测 12 个抽样词**覆盖率全部回到 100%**。

#### 问题 2：子串回退假阳性（比漏检更危险）

`kb_read.py::cmd_find` 的回退逻辑在第一个"能出结果的窗口尺寸"处 `break`：

```python
for size in (3, 2):
    ...收集窗口...
    if merged:
        break        # ← 只要某个 3 字片段有结果就收工
```

于是查询一个全库**根本不存在**的短语时，只要它的某个 3 字片段存在，
就返回那个片段的结果。实测查询「不存在词xyz」（真值命中 **0** 处）
返回了「136 个文件 / 400 处」，且输出标题写着"命中"。

**这是检索里最坏的一类错误**：结果看起来正常、条数还挺多，
使用者不会怀疑，会把不存在的表述写进方案。

**修法**：新增 `_verify_lines()`，回退结果**一律逐行回原文核对**，
只有该行真的含完整查询串才保留。核对不过就如实报「未命中」。
交集路径也套用同一核对（实测「表土剥离厚度」曾多报 1 处）。

#### 问题 3：2-gram 交集塌缩 + 窗口列表被截断

`_ngram_candidates()` 有两处缺陷：

1. 窗口在索引里缺失时**静默 `continue` 跳过**，然后对"剩下的窗口"求交集——
   数学上不成立，且缺失关键窗口时交集会异常小；
2. 返回时 `sets[:max_terms]`（max_terms=8）**截断窗口列表**，
   长查询会丢掉部分窗口，"交集"退化成"前 8 个窗口的交集"。

实测「水土保持」只报 **8 个文件 / 332 处**（真值 321 文件 / 45796 处）。

**修法**：不再截断窗口；缺失窗口显式返回并由调用方**告警**；
输出中明确标注"该结果是索引近似（精确、无假阳性，但不保证 100% 召回）"
并给出 `kb_lookup.py --find` 的全量替代方案。

修复后：

| 查询 | 修复前 | 修复后 | 真值 |
|---|---|---|---|
| 水土保持 | 8 文件 | **256 文件** | 321 |
| 防治标准 | 3 文件 | **69 文件** | 132 |
| 林草覆盖率 | 9 文件 | **78 文件** | 128 |

### 10.3 踩过的坑（新增）

**坑 17：注释与代码不一致，且"看起来对"**
`# 只保留前 N 个文件` 与 `postings[:max_postings]`（取前 N 处）语义完全不同。
两处都在同一个函数里、相隔 3 行，肉眼极易滑过。教训：**注释里的量词
（文件/处/行）必须与代码的实际操作对象逐一核对**。

**坑 18：静默截断比报错危险得多**
三处问题都不是崩溃，而是"安静地返回一个错得离谱的小结果"。
`--limit 3 | Select-Object -First 3` 这种输出截断还一度让我误判
`kb_lookup --find` 有 bug（实际它正确报告了 16778 处）。
教训：**验证工具的输出本身也不能被截断**，必须看完整的统计行。

**坑 19：自检脚本抓到自己引入的 bug**
新增 `zc1` 键后 `selfcheck2.py` 报 `无法反查的键：['zc1']`（23/24）。
这是自检脚本**正确工作**，不是脚本过时。修法是**补文档 + 注册 KEY_ALIAS**，
而不是把 `zc1` 加进白名单绕过检查。

**坑 20：真值口径错了会造出假问题**
用 `'Newsletter12' in line` 做真值时，原文 `Threatened Plants Newsletter 12:14`
（**带空格**）被判为"不一致"，看起来像索引假阳性；实际索引按标准号规则
把 `Newsletter 12` 识别为整串，**行为正确**。
同理 `466` 的"漏检"是因为真值用子串匹配而索引用 token 匹配
（`25466` 含 `466` 但 token 是 `25466`），**索引更精确**。
教训：**测真值的口径必须与索引的语义一致**，否则量出来的全是噪声。

### 10.6 补记：精确命中路径的截断提示（同源问题，一并修复）

10.2 的问题 1 修完后，我复查发现**精确命中路径同样静默截断**，只是表现形式不同：

```
kb_read.py  --find 表土   →  「精确命中：251 个文件 / 400 处」
kb_lookup.py --find 表土  →  「共命中 16778 处」
```

**差 42 倍，而旧输出只有一行"精确命中"，使用者会以为全库就 400 处。**
这正是坑 18 说的"静默截断"——问题 1 修的是**截断策略**（谁被保留），
这里补的是**截断告知**（告诉使用者被截了）。

**判据**：总处数 `>= 400`（预算上限）。只有撞到预算才会刚好卡在这个整数上，
是截断的可靠信号；未截断的词不会这么巧。
实测验证了判据的双向正确性：

| 词 | 索引处数 | 全库真实处数 | 是否提示 |
|---|---|---|---|
| 表土 | 400（满） | 16778 | ✅ 提示 |
| 沉沙池 | 400（满） | 4479 | ✅ 提示 |
| 截水沟 | 400（满） | 1985 | ✅ 提示 |
| GB/T 50434-2018 | 118 | 118 | ❌ 不提示（未截断） |

顺带修掉自己写这段提示时引入的 **`%` 格式化崩溃**：
`print('…100% 覆盖…' % word)` 里的 `%` 被当成格式符，
触发 `TypeError: not enough arguments for format string`。
**`kb_read.py --find` 的每一条查询路径都因此崩溃**（`--limit` 一跑就 traceback）。
教训补充为**坑 21：在 `%` 格式化的字符串里写字面量百分号必须写 `%%`**——
而且这类错误只在**该分支真的被执行到时**才暴露，冒烟测试必须覆盖到每条分支。

**验收**：`表土` / `水土保持` / `陇东黄土` / `沉沙池` / `GB/T 50434-2018`
五条查询全部 `exit=0`、无 traceback。

## 十二、图片压缩专项：三次失败与最终结论（2026-09）

> 用户要求压缩技能包体积（552.3 MB，其中图片 391.2 MB 占 70.8%）。
> 本节记录**三次真实翻车**，全部有据可查。**结论：P0 不可自动化。**

### 12.1 战场定位（实测）

| 项 | 数值 |
|:--|:--|
| 包总量 | **552.3 MB** |
| vault | 503.0 MB（371 个 md） |
| references | 48.5 MB（索引 41.5 MB） |
| 正文文字 | 111.8 MB |
| **内嵌图片** | **391.2 MB（占 md 的 77.8%）** |
| 图片数 | 8510 张，**全部 jpeg**，平均 **694×457** |

### 12.2 传统压缩全部无效（实测，非估算）

| 方案 | 样本 | 实测节省 |
|:--|:--|:--|
| 转 WebP q82 | 158 张分层 | **3.6%** |
| JPEG 重编码 optimize | 400 张 | **0.0%（400/400 反而变大）** |
| 灰度化 | 500 张 | **0.0%（440/500 本就是灰度）** |
| 降分辨率至 1600px | 500 张 | **0.0%（无图超过 1600）** |
| 去重 | 全库 | **≈0（跨文件重复 0 组）** |

**根因**：图片经 MinerU 下游流水线处理过，**已被压到接近极限**。

### 12.3 【翻车一】按行号删除 → 删错，破坏正文

**做了什么**：用扫描得到的候选图**行号**去删图。

**为什么错**：脚本**边删边写**，文件行数变化后**后续行号全部漂移**，
删掉的是别的行 —— **删掉的是图注和正文**。

**证据**（回滚对比时发现）：
```
原: 图1 排水工程组成和相互关系      ← 图注被删
现: ![](data:image/jpeg;base64,...)  ← 而图还在
```
受损行还包括 `定价：50.00元`、`# 水土保持设计手册`、`二〇〇六年二月二十八日` 等**真实正文**。

**修复**：立即从 `bak_p0` 完整回滚，校验 **8510 张图 / 503.0 MB** 复原，回归 18/18 全绿。

**教训（坑 24）**：**绝不用行号定位**。必须用**内容 sha256**。

### 12.4 【翻车二】关键词判"封面图" → 大面积误报

**做了什么**：改用 sha256 定位后，用"图片上下文 12 行内出现 ≥2 个版权词（定价/ISBN/出版/CIP…）"判定封面图。

**结果**：候选从 78 张**暴涨到 184 张**，省 12.20 MB。

**为什么错**：`出版` `出版社` `ISBN` `CIP` 是**参考文献里的高频词**，
不是封面特征。抽样核对发现大量误报：

| 被误判的图 | 真实内容 |
|:--|:--|
| `参考_王家臣…L8620` | **三维有限元网格模型图**（技术图） |
| `ex17…L7740` | **彩色工程实景航拍照片** |
| `中国水土保持_2024…` | **表土剖面现场照片（带手势比例尺）** |

**教训（坑 25）**：**关键词 ≠ 机制**。词在文中出现，不等于该图是封面。
这与此前记录的"坑 22"同源 —— **判据必须来自结构，不能来自词表**。

### 12.5 【翻车三】结构特征量选反了 → 把照片当条码

**做了什么**：放弃关键词，改用纯结构特征：`colorful`（彩色度）+ `darkcols`（全暗列数）。

**结果**：命中 285 张，**全部**被判为 `R1_条码二维码`，省 18.18 MB。

**为什么错**：`darkcols` 高（127）**不等于条码** —— 它只说明**整图偏暗**。
实抽样核对：

| darkcols | 真实内容 |
|:--|:--|
| **127** | **遥感/地貌影像，带 ①②③ 编号标注点**（技术图） |
| **18** | **表土现场照片**（带手部比例尺） |

**关键**：`darkcols=127` 意味着**127 列全是暗的** = 整图暗，
这与条码的"交替黑条"**正好相反**。**指标方向选反了。**

**教训（坑 26）**：**设计判据前必须先看样本**。
我连看都没看就跑了全库，算出 285 这个数字**毫无意义**。

### 12.6 最终结论：P0 不可自动化，收益也不值

**三个硬事实**：

1. **判据不可靠**：三次判据（行号/关键词/结构）**三次错**，且每次都错在**删掉真内容**上。
2. **收益极小**：即便最乐观的 78 张估算，也只有 **3.8 MB / 552.3 MB = 0.7%**。
3. **风险不对称**：删错一张**技术图或现场照片**，损失的是**不可再生的判据证据**；
   省下的 0.7% 体积**毫无意义**。

**决定：P0 不做**。图片保留原样。

> 这符合本技能一贯纪律：**宁可不做，不可做错**。
> `kb-and-tokens.md` 的"逐字引用不可改"、`human_voice` 只设 warning 不设阻断，都是同一条原则。

### 12.7 唯一仍然成立的杠杆

| 方案 | 收益 | 风险 | 状态 |
|:--|:--|:--|:--|
| **P1 图片剥离到包内 `.assets/`** | **省 97.8 MB（17.7%）** | 中，但可脚本化+可回滚 | 待评估 |
| P2 MinerU 云端结构化 | 待定 | 低 | 通道已验证 |
| P0 删封面图 | 0.7% | **高（已三次翻车）** | **否决** |

**P1 才是真正的大杠杆**：base64 膨胀率 4/3，剥离后省 97.8 MB，
且**检索通道从 503 MB 降到 111.8 MB（-77.8%）**。
它是**纯机械变换**（base64 → 二进制 + 相对路径），**可逐张 sha256 校验、可一键回滚**，
不像 P0 需要"判断这张图有没有价值"这种**不可靠的语义判断**。

删掉它们 → 该章节只剩一堆无意义的文字标签，读者再也无法照着操作。

### 15.3 另一个反例：土地利用图

`30f1103a/0014.jpg` 原始内容 = **《某小流域水土保持措施布局图》**
（彩色分区、图斑编号 1~37、图例 II/III/IV/XI、指北针、比例尺 1:10000）。

MinerU 判定 `['table','table','image']`，提取 1077 字 ——
**但那 1077 字只是图纸角落里的统计表**。按规则这张图会被删（省 388 KB），
而**整张布局图（措施空间分布）随之消失**。
MinerU 自己把地图切成了单独的 `image` 块（353 KB），说明它知道那不是表格。

### 15.4 结论

**「能转成文本」≠「转完可以删图」。** 这是两个不同的问题：

* MinerU 回答的是：**这张图里有没有能认成文字的东西**
* 删图需要回答的是：**把能认的文字拿出来后，图里还剩不剩东西**

MinerU 的判定**不能证明后者**。真实可删量 = **0**。

**这与 P0 三次翻车同源**：都需要一个「这张图有没有价值」的
**不可靠语义判断**，而收益（49.5 MB 表面值 / 实测 0）远不足以承担风险。

### 15.5 采用的替代方案：**增量旁注（只增不减）**

用户批准改做加法：

* 原图 **100% 保留**（磁盘不动、md 引用不动）
* 在图片引用行**之后追加**一段旁注：

```
![](../../.assets/xxx/0001.jpg)
<!-- mineru:begin -->
> **自动提取的图内文本（原图保留，仅供参考）**
> | 措施名称 | 单位 | 数量 | 措施名称 | 单位 | 数量 |
> |---|---|---|---|---|---|
> | 梯田 | hm2 | 34.25 | 灌木林地 | hm2 | 26.15 |
<!-- mineru:end -->
```

**收益**：图片里的数字/参数进入倒排索引，`kb_lookup --find` 可命中（原先搜不到）。
**代价**：文本约几 MB（净增），包体积略涨。
**风险**：**零** —— 纯追加，`p2_batch.py --rollback` 一键撤销。

### 15.6 旁注清洗（必须做，否则全是噪音）

MinerU 的 HTML 表格里混着**图签**（图纸右下角标题栏）：

```
| 核定 |  |  | 设计阶段 |
| 审查 |  |  | 水保部分 |
| 制图 |  |  | 某小流域水土保持措施布局图 |
| 比例 | 1:10000 |  |  |
```

**这些不是表格内容**，必须按关键词剔除，否则旁注一半是噪音。
已实现：`p2_annotate.clean_text()` 过滤
`核定|审查|校核|制图|资质证号|设计证号|图号|日期|比例 1:`。

### 15.7 本轮新增踩坑

**35. "能转文本"不等于"可以删图"。**
实测 100 张：表面可删 17 张，复核后**真正可删 0 张**。
软件截图、断面图的文字多 → 容易被误判为"纯文字可删"。

**36. 软件界面截图是"文字陷阱"重灾区。**
截图里文字密集，MinerU 提取成 text 且不给 image 块，
规则会判定"可删"。但**截图本身就是操作说明的内容**。

**37. 旁注必须过滤图签。**
MinerU 会把图纸标题栏（核定/审查/制图/图号）也当表格提取，
不过滤则旁注充满噪音。

**38. 图片引用的路径匹配不能只比 basename。**
不同 md 会生成相同 tag（如两个文件都有 `30f1103a/`），
必须把 `../../` 归一化后按 assets 相对路径严格比对。

**根因**：匹配到别名「总投资」后，紧接着是 ` | 万元 | `，
与 `SEP` / `unit_pattern` 期望的形态不符 → `continue` 放弃。

**而这不是边角情况**：开采方案/可研的核心数值几乎全部以表格承载
（主要技术经济指标表、土石方平衡表、占地表、投资估算表），
估算占全部字段的 **57%**。原实现等于放弃了一多半的自动抽取能力。

C 档唯二抽到的值还是**串值污染**：`"— | 某某煤矿"`——
把表格分隔符吃进了值里，**比抽不到更危险**（看似有值，会误导下游）。

### 16.2 对策：展平，而不是改匹配规则

新增 `flatten_tables(text)`，在**抽取之前**把表格行规范成叙述形态：

```
输入  | 序号 | 指标名称 | 单位 | 数量 |
      | 1    | 总投资   | 万元 | 286500 |
输出  总投资：286500 万元
```

**关键设计：不改匹配逻辑，只改输入形态。** 因此：

- 现有别名表、单位规则、weak 机制**全部原样复用**，行为可预期
- 原文行**原样保留**在输出中 → 出处行号与 `snippet` 仍指向原表，可回溯
- 仅当「指标名」命中已知字段别名时才展平，避免把任意表格变成伪叙述句

展平结果与原文抽取结果**合并去重**后共同进入候选，展平命中标 `from_table=true`。

### 16.3 单位容错：从丢弃改为降级

**旧行为**：数值字段声明了单位，但文本中未出现单位 → **直接丢弃该候选**。

**问题**：单位常写在表头、或整段统一声明。正文里「总投资 286500」不带单位是
极常见写法，旧行为会漏掉大量**真实命中**。

**新行为**：降级为弱候选（`weak=true, unit_missing=true`）保留，不参与冲突判定，
补数清单提示「单位待核实」。**复用既有 weak 机制，不新增状态语义。**

### 16.4 实测效果

真实形态文档（正文段 + 表格混排，17 个目标字段）：

| 项 | 优化前 | 优化后 |
|:--|--:|--:|
| 正文字段 | 100% | **100%**（未下降） |
| 表格字段 | 0–22% | **100%** |
| 串值污染 | 有（`"— | 某某煤矿"`） | **0** |
| 综合准确率 | 约 47% | **17/17 = 100%** |

**不编造铁律仍成立**：只给 1 个字段的表格，仍只抽出 1 个，其余留待填。

### 16.6 本轮新增踩坑

**39. 序号列会被误当取值。**
`| 1 | 总投资 | 万元 | 286500 |` 展平后曾抽出 `1` 而非 `286500`——
因为「序号」也是数字列，排在「数量」之前。
必须按表头名排除 `序号|编号|No.|ID`，且该规则对「序号在中间」的表格同样有效。

**40. "抽取能转"不等于"抽取准确"。**
第一版展平把 7 个字段全部"抽到了"，但**值全是序号**。
**只有逐字段比对具体数值**才能发现——只统计"抽到几个"会得出错误结论。
这条与踩坑 35 同源：**数量指标会掩盖质量缺陷。**

**41. 表格展平必须保留原文行。**
若只输出展平句而丢掉原表，`snippet`/行号就指向不存在的行，**出处回溯断裂**。
技能的核心承诺是"每个取值都带出处"，展平不能破坏它。

**42. 优化开关必须落在 rules.json。**
`table_flatten.enabled` / `unit_missing_tolerant` 均可在 rules 里一键退回旧行为，
代码不自带阈值——与技能既有约定一致（"脚本只执行 rules 里的规则"）。
